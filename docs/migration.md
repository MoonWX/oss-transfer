# Upgrade from v4.0.x

[中文](migration.zh-CN.md)

This page is for users still running v4.0.x who plan to upgrade to v4.1.x. Follow the steps on this page to convert your existing data to the current version.

Data from v4.0.x cannot be used directly in v4.1 or later and requires a one-time offline conversion. The converter preserves accounts, storage connections, node limits, task history and the recycle bin. Unfinished tasks are not lost; they enter the new installation in a stopped state, ready for you to resume manually after you have confirmed that everything is in order.

For a fresh installation with no existing data, see the [installation instructions](install.md). If you are already running v4.1 or later, upgrade through [software updates](operations.md#software-updates).

## Convert an existing installation

The process has five steps:

1. Stop the old Master and all Agents (execution nodes). Back up each node's database and configuration. Record any overrides set through environment variables or command-line arguments as well.
2. Export each node's RocksDB data. If the old Master also performed transfers, export it as well.
3. Write a migration plan that specifies node identities, effective limits, the Master address and the final data paths.
4. Run preparation and finalization in a new directory.
5. Install native services using the `service.json` generated by the converter. Confirm that the Agents are online, then resume the tasks you want to continue.

The commands for each step and the migration plan format are in the [conversion guide](development/legacy-migration.md). Preparation and finalization run on both Linux and macOS, including older kernels that lack `renameat2`. Do not remove the original installation or backups until the new services and task results have been verified.

v4.1 introduces an architectural change: scheduling and execution are separate. The Master handles scheduling only; Agents carry out the data transfers. A single-host deployment therefore requires both roles, each with its own data directory. In a cluster deployment, place each finalized Agent directory on its corresponding execution host. The path must match the absolute path recorded in the configuration.

An Agent retains its original identity when its private credentials match the Master snapshot. Directly addressed v4.0.x workers receive new identities through explicit entries in the migration plan. After conversion, sign in with the existing account password. Old login sessions are invalidated, so you will need to sign in again.

## Resume unfinished tasks

After conversion, unfinished tasks are in a stopped state. The first manual resume rescans the original scope using the task's saved ranges, inventory, filters and target naming rules.

A resume is not a blind replay. Before reusing an old successful result, the Agent reads the current source and destination objects and compares their SHA-256 hashes. It also verifies that neither side's identity changed during the reads. A source object that no longer exists is recorded as failed. When the destination contains an object with the same name but different content, the task's saved [conflict policy](operations.md#conflict-policies) applies: `SKIP` (*Skip existing objects or files*) leaves the destination object unchanged; `OVERWRITE` (*Overwrite existing objects or files*) writes it again. Objects previously excluded by a time filter remain excluded after the resume.

The v4.0.x database does not store multipart upload IDs or completed-part lists. Interrupted multipart uploads can only restart at the object level; they cannot be resumed mid-upload.

Completed tasks are not affected. Their historical results and coverage statistics are preserved. New transfer attempts are recorded separately and do not mix with the old results.

> Review the retry, concurrency and multipart [defaults](development/legacy-migration.md#execution-defaults) in the conversion guide before setting `acceptGoRuntimeDefaults` in the migration plan.
