# 从 v4.0.x 升级

[English](migration.md)

本页面向仍在使用 v4.0.x、计划升级到 v4.1.x 的用户。按照本页步骤操作，即可将旧数据转换至当前版本并正常运行。

v4.0.x 的数据无法直接在 v4.1 及以后的版本中使用，需要先离线转换一次。转换工具会将账号、存储连接、节点限制、任务历史和回收站一并保留。未完成的任务不会丢失，转换后处于已停止状态，待你确认一切正常后再手动恢复。

如果你是全新安装，不涉及旧数据，直接参考[安装说明](install.zh-CN.md)。已在使用 v4.1 或更高版本的，通过[版本更新](operations.zh-CN.md#版本更新)升级即可。

## 转换现有安装

整个过程分为五步：

1. 停止旧的 Master 和所有执行节点（Agent），备份每个节点的数据库和配置。环境变量和命令行参数中的覆盖配置也需要记录。
2. 导出每个节点的 RocksDB 数据。旧 Master 如果也执行过传输任务，同样需要导出。
3. 编写一份迁移计划，写明节点身份、实际生效的限制、Master 地址和最终数据路径。
4. 在一个新目录中执行准备和最终发布。
5. 使用转换工具生成的 `service.json` 安装原生服务。确认执行节点上线后，再恢复需要继续执行的任务。

每一步的具体命令和迁移计划格式见[转换指南](development/legacy-migration.zh-CN.md)。准备和最终发布在 Linux 和 macOS 上均可运行，包括缺少 `renameat2` 的较旧内核。新服务和任务结果核对无误之前，不要删除原有的安装和备份。

v4.1 有一个架构上的变化：调度与执行分离。Master 只负责调度，数据传输由执行节点完成。因此单机部署也需要安装两个角色，Master 和执行节点各自使用独立的数据目录。集群部署时，将转换完成的每个执行节点目录移至对应的执行主机上。路径需要与配置中记录的绝对路径一致。

如果执行节点的私有凭证与 Master 快照一致，它会保留原有身份。v4.0.x 中直接寻址的 worker 通过迁移计划中的显式条目获得新身份。转换完成后使用原来的账号密码登录，但旧的登录会话会失效，需要重新登录一次。

## 恢复未完成的任务

转换后，未完成的任务处于已停止状态。首次手动恢复时，系统按任务当初保存的范围、清单、过滤条件和目标命名规则，重新扫描原来的范围。

恢复不是盲目重新执行。复用旧的成功结果之前，执行节点先读取当前的源端和目标端对象，比较 SHA-256 哈希。读取前后还会检查两端的身份是否发生变化。源端对象已不存在的，记为失败。目标端存在同名对象但内容不一致的，按任务保存的[冲突策略](operations.zh-CN.md#冲突策略)处理。策略为 `SKIP`（跳过同名对象或文件）时，目标端对象保持不变，为 `OVERWRITE`（覆盖同名对象或文件）时则重新写入。之前被时间过滤排除的对象，恢复后仍然排除。

v4.0.x 的数据库中未保存分片上传的 upload ID 和已完成分片列表。中断的分片上传只能从对象级别重新开始，无法续传。

已完成的任务不受影响，历史结果和覆盖范围统计均会保留。新的传输尝试单独记录，不与旧结果混合。

> 在迁移计划中设置 `acceptGoRuntimeDefaults` 之前，先查阅转换指南中关于重试、并发和分片上传的[默认值](development/legacy-migration.zh-CN.md#执行默认值)。
