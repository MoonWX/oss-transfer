## 排障

从你看到的现象入手。控制台和 CLI 的错误信息会先给出简短的原因和处理建议；原始错误在控制台中点击 **显示原始错误** 查看，在异常记录中位于提示框内，CLI 加 `--verbose` 显示。

### 存储连接检查失败

带 **保存时验证访问权限** 保存连接、**测试连接**、**创建迁移** 中的存储桶列表、`storage test` 和 `storage buckets` 都执行同一项检查。Master 让一个在线的执行节点（Agent）执行它，因此需要访问 Endpoint 的是该执行节点而不是 Master，域名也由该执行节点的 DNS 解析。检查内容：

1. 列举存储桶（ListBuckets）；
2. 用实际生效的寻址方式，在指定的存储桶（未指定时为列出的第一个存储桶）中列举最多一个对象（ListObjectsV2）。

最多尝试 3 次，总时长不超过 20 秒。没有在线执行节点时，提示 *没有在线执行节点，请先添加执行节点再测试连接。*

| 提示（节选） | 可能原因 | 处理方法 |
| --- | --- | --- |
| *无法解析存储桶域名 …。自建 S3（MinIO、SeaweedFS、Ceph 等）需要 Path-style* | Virtual-hosted 寻址把存储桶放进域名（`bucket.s3.example.com`），自建存储通常无法解析 | 在控制台点击 **改用 Path-style**，或运行 `oss-transfer-cli storage update 连接名 --path-style true` |
| *以存储桶域名访问时，存储服务关闭了连接（EOF）* | 同一问题，以 EOF 的形式出现 | 同上，改用 Path-style |
| *无法解析 Endpoint 主机名 …* | 主机名写错，或执行节点的 DNS 无法解析 | 检查 Endpoint，并在执行节点主机上运行 `nslookup 主机名` |
| *… 关闭了连接（EOF），请检查 Endpoint 地址、端口和协议* | 对 HTTPS 端口使用了 `http://`（或相反），或端口错误 | 修正 Endpoint 的协议和端口 |
| *… 拒绝了连接* | 该地址和端口上没有服务在监听，或存储服务已停止 | 检查 Endpoint，确认存储服务正在运行 |
| *与 … 的连接被重置* 或 *连接 … 超时* | 协议不匹配，或执行节点与 Endpoint 之间有代理、防火墙 | 在执行节点主机上检查网络，例如运行 `curl -v Endpoint` |
| *无法验证 … 的 TLS 证书* | 自签名或私有 CA 证书，或对没有 TLS 的服务使用了 `https://` | 让执行节点主机信任该证书；服务没有 TLS 时改用 `http://` |
| *Access Key 不存在，请检查 Access Key。* | Access Key 错误，或属于其他账号、其他区域 | 检查 Access Key |
| *签名不匹配，请检查 Secret Key 和签名版本。* | Secret Key 错误，或服务只接受 V2 签名 | 检查 Secret Key；只有服务确实需要时才选择 V2（`--v2-signer true`） |
| *存储桶 … 不存在* | 存储桶名称、Endpoint 或区域错误 | 逐项检查 |
| *访问被拒绝：凭据有效，但没有执行此请求的权限。* | 密钥缺少权限 | 按[规划](planning.zh-CN.md)中的权限清单授权 |

以下两种结果只是警告，不是错误：连接会保存，并且可以使用。

- *该凭据无权列举存储桶（ListBuckets 被拒绝）…*：密钥只授权到单个存储桶。创建任务时直接填写存储桶名称；可在 **测试连接** 窗口的 **检查指定存储桶** 中检查它，或运行 `oss-transfer-cli storage test 连接名 --bucket 存储桶`。
- *该凭据无权列举存储桶 … 中的对象（AccessDenied）…*：从该存储桶迁移前，请检查它的权限。

**寻址方式。** 默认的 **自动（推荐）** 在 Endpoint 带端口，或主机为 IP 地址、`localhost`、不含点的主机名、以 `.internal`、`.local`、`.lan` 结尾时使用 Path-style，否则使用 Virtual-hosted。表单会显示当前 Endpoint 实际使用哪一种，连接卡片显示 *自动 · Path-style* 或 *自动 · Virtual-hosted*。规则不适合你的服务时（例如通过不带端口的域名访问的自建存储），请明确选择 Path-style 或 Virtual-hosted。自动寻址和存储桶级检查由执行节点完成：低于 v4.1.42 的执行节点会把未明确选择寻址方式的连接当作 Virtual-hosted，并且只列举存储桶（测试窗口会提示节点版本较旧）。

### 执行节点离线

**执行节点** 页面显示每个节点的状态。等待离线节点的任务会提示 *执行节点 … 离线，任务等待其恢复连接*，并列出每个节点最后连接的时间。

1. 在执行节点主机上检查服务和日志末尾：

   ```sh
   sudo systemctl status oss-transfer-agent
   sudo tail -n 50 /opt/oss-transfer/agent/data/logs/service.log
   ```

2. 确认该主机能访问加入时使用的 Master 地址：`curl -fsS http://MASTER:1685/healthz` 正常时输出 `{"role":"master","success":true}`。执行节点主动连接 Master，Master 从不连接执行节点。
3. 如果 `systemctl status` 显示 `failed` 和 `status=78`，说明该执行节点已在 Master 上被移除并按设计停止（见[移除执行节点](#移除执行节点)）。可以从 **执行节点 → 添加节点** 复制新的加入命令重新加入，或[卸载](install.zh-CN.md#卸载)它。
4. Docker 执行节点使用 `docker ps -a` 和 `docker logs 容器名` 检查。

执行节点离线期间，它的子任务会等待。多节点任务中，在节点支持的情况下，大约 70 秒后其未完成的子任务会转到其他节点（见[失联节点](#失联节点)）。

### 任务卡住或速度慢

打开任务详情（或运行 `oss-transfer-cli task show ID`）：

1. 先看“需要关注”提示，它会指出离线节点或主要的失败原因（见[任务详情](#任务详情需要关注与失败摘要)）。
2. 对比 **请求速率** 表中的 **实时** 和 **生效上限**。速率一直贴着上限，说明是限速在约束任务：用 **调整** 提高任务限速，或在 **执行节点** 页面提高节点限速。每个节点默认 2,000 Mbps 带宽、每秒 100 次 LIST（见[节点限速](#节点限速)），高速网络上请调高。
3. 节点卡片显示 *自动降速*，说明存储服务正在限流，执行节点是在主动放慢（见[存储限流](#存储限流)）。
4. 大量小对象的速度取决于请求延迟而不是带宽。提高[节点并发](#节点并发)或增加执行节点（见[调整任务的执行节点](#调整任务的执行节点)）。
5. 任务先列举源端。扫描找到对象之前不会开始传输；重启后扫描从断点继续（见[断点续扫](#断点续扫)）。

`oss-transfer-cli task nodes ID` 显示每个节点分到的任务限速份额以及是否繁忙。

### 对象失败

失败的对象位于 **异常记录 → 失败对象**（上传和下载位于 **本地迁移失败**）。列表默认只显示未解决的记录，每条都有简短原因，打开记录可查看完整错误。CLI 运行 `oss-transfer-cli exceptions list failed --task-id ID`。任务详情也会显示主要原因（见[失败摘要](#任务详情需要关注与失败摘要)）。

| 原因 | 处理方法 |
| --- | --- |
| 存储拒绝访问，或访问密钥无效 | 修正密钥或其权限（见[规划](planning.zh-CN.md)），然后重试 |
| 存储桶不存在，或无法解析存储地址 | 修正存储连接（存储桶名称、Endpoint、寻址方式），然后重试 |
| 连接被拒绝、被中断或超时，或存储服务端出错 | 存储不可用的时间超过了重试能覆盖的范围（见下一节）。存储恢复后重试 |
| `exceeded maximum number of attempts, 10`，并带有 `SlowDown` 等错误码 | 限流持续太久。调低限速（见[存储限流](#存储限流)），然后重试 |
| 执行节点没有本地目录的读写权限 | 为执行节点的服务账号授权（Docker 执行节点为 UID 65532），然后重试 |
| 目标磁盘空间不足，或目标文件系统为只读 | 释放空间或修正挂载，然后重试 |
| 源对象在扫描后发生变化 | 直接重试，会复制其当前版本（见[源对象被修改](#源对象在扫描后被删除或修改)） |

在任务详情或 **异常记录** 页面点击 **重试失败项**，或运行 `oss-transfer-cli task retry ID`。只有失败的对象会重新传输。另见[重试、继续与恢复](#重试继续与恢复)。

### 存储服务中断或网络断开

执行节点能挺过短暂的中断。请求因连接被拒绝、重置或中止、管道断开、超时、DNS 临时故障或 HTTP 5xx（501 和 505 除外）失败时，最多尝试 10 次，等待时间从约 1 秒逐步增加到 20 秒，总计约 1 到 2 分钟，之后对象才记为失败。被限流的请求同样最多尝试 10 次（见[重试](#重试)）。执行节点启动后已经应答过的存储主机，出现以下两种失败时也是如此：连接在收到响应前结束（`EOF`，例如存储服务在请求进行中被停止），以及主机名不再能解析（例如已停止的容器名）。对于从未应答过的主机，这两种失败说明 Endpoint 或寻址方式有误，按常规尝试 3 次后失败；主机名不存在则立即失败。拒绝访问等错误会立即失败。

读取对象期间源端中断时，源端恢复应答后会从中断的字节处继续读取，并固定为开始时的版本（期间被替换的对象按“已变化”失败）。每次重试都会写入执行节点的[服务日志](install.zh-CN.md#日志)，最多每 30 秒一行。

中断时间更长时，受影响的对象会以连接或服务端原因失败，存储恢复后重试即可。中断期间未能中止的分片上传会在之后中止：该节点上的任务开始、继续或重试时，每次子任务执行结束后，仍有未中止的上传时每 5 分钟一次，以及执行节点启动时。连接检查仍在 3 次尝试后放弃。

### 源对象在扫描后被删除或修改

任务先列举源端，之后才传输，两者之间对象可能发生变化：

- **在源端被删除**（源为对象存储时）：扫描后、迁移前在源端被删除的对象不算失败，计为跳过，也不会出现在异常记录的失败对象中。[任务报告](#任务报告)的 `file-results.csv` 中列出该对象，结果为 `SKIPPED`，原因代码为 `SOURCE_DELETED`。`task show` 和任务详情中关于跳过的提示会同时说明这两种跳过原因。本地源目录中缺失的文件仍记为失败。
- **在源端被修改**：该对象失败，原因代码为 `SOURCE_CHANGED`（*源对象在扫描后已变化，重试会读取其当前版本*）。**重试失败项** 会复制重试时的当前版本，任务的总大小也按新大小计算。报告把该对象标记为 `SOURCE_REFRESHED`。

对象复制完成之后才发生的修改，本次任务不会发现。请保持源端稳定，或使用多轮增量迁移并在最后做一次比对（见[规划](planning.zh-CN.md)）。

### 下载预检失败

下载到本地目录前，每个执行节点会在目标目录（或其最近的已存在上级目录）中写入并删除一个探测文件（`.oss-transfer-write-probe-*`）。通过时显示 *目标目录可写，可用空间 12.3 GiB*（或 *目标目录将在任务开始时创建* 加可用空间）。失败时显示原因：

| 提示 | 处理方法 |
| --- | --- |
| *节点无权写入 /files：Agent 以 UID 65532 运行，请将该目录授权给此用户（例如 chown 65532）* | 为该 UID 授予写权限，例如在 Docker 主机上运行 `sudo chown -R 65532 /files` |
| *节点无权写入 …，请为 Agent 服务账户授予写权限* | 为服务账号（原生安装为 root）授予写权限，或检查挂载选项 |
| *… 所在文件系统为只读，无法下载到此目录* | 以读写方式挂载该目录 |
| *… 所在磁盘已无剩余空间* | 释放空间或换一块磁盘 |
| *… 不是目录，无法作为下载目标* | 选择一个目录 |

CLI 中对应的预检字段为 `writeProbeDirectory`、`effectiveUid` 和 `freeBytes`（`--validate-only` 只运行预检，不创建任务）。低于 v4.1.42 的执行节点仍使用不写探测文件的旧检查。

### 下载目录中的暂存目录

下载时，数据先写入目标文件旁的隐藏目录 `.oss-transfer-staging-…` 中的临时文件，完整后才以最终文件名发布（见[临时文件](#临时文件)）。没有任何执行过程再使用某个暂存目录时，执行节点会删除它；执行节点启动时也会清理空的残留目录。仍然存在的暂存目录可能属于尚未完成的任务；该目录仍有任务写入时，请保留它。

## 重试、继续与恢复

以下操作都不会重复传输已完成的对象。

| 任务状态 | 控制台 | CLI | 实际行为 |
| --- | --- | --- | --- |
| 运行中，且有失败对象 | **重试失败项** | `task retry ID` | 重新传输已结束子任务中的失败对象，任务继续运行（见[详细说明](#运行中任务重试失败项)） |
| 已停止 | **继续传输** | `task resume ID` | 扫描从断点继续，处理未完成和失败的对象 |
| 部分失败 | **重试失败项** | `task retry ID` 或 `task resume ID` | 开始新的一轮，传输失败和未处理的对象；成功和跳过的对象保留结果 |
| 失败 | **重试任务** | `task retry ID` 或 `task resume ID` | 与部分失败相同；因错误停止的扫描从停止的位置继续 |
| 已完成 | — | — | 无需操作。要同步源端之后的变化，请新建任务（见[增量迁移](#冲突策略)） |

- **停止**（`task stop ID`）会保留全部进度。已停止的任务随时可以继续，Master 或执行节点重启后也可以。
- 可以在任务列表中一次继续或重试多个任务；所选任务同时包含已停止和失败的任务时，按钮显示为 **恢复任务**，两种操作一并执行。
- `task recover-child ID-N` 让节点立即继续一个可恢复的子任务。
- 重试会重新读取源端：扫描后被修改的对象按当前版本复制。
- [对象比对](#对象比对)单独继续：**继续比对** 或 `object resume ID` 从检查点之后继续被中断、失败或已取消的前缀比对。

## 迁移选项

这些选项在 **创建迁移** 中或用 `task create` 设置（见 [CLI](cli.zh-CN.md#创建任务和设置限速)）。除非另有说明，任务创建后不能再修改。

### 冲突策略

**目标已存在时** 决定目标端已有同名对象或文件时怎样处理：

| 策略 | CLI | API | 效果 |
| --- | --- | --- | --- |
| **跳过同名对象或文件**（默认） | `--conflict skip` | `SKIP` | 保留已有的对象或文件，不比较大小和内容 |
| **覆盖有变化的对象** | `--conflict changed` | `OVERWRITE_CHANGED` | 只有目标看起来已过时（规则见下）才覆盖，其余跳过 |
| **覆盖同名对象或文件** | `--conflict overwrite` | `OVERWRITE` | 覆盖所有已存在的对象或文件，全部重新传输 |

目标端不存在的对象总是会被复制。选择 **覆盖有变化的对象** 时，满足以下任一条件就覆盖已有的目标对象：

1. 大小不同；
2. 两边的 ETag 都是普通 MD5 ETag（32 位十六进制）且不同；
3. 源端的修改时间（Last-Modified）晚于目标端。

否则跳过，计为跳过。判断只使用列举得到的元数据，从不读取对象内容。分片上传的 ETag（`…-N`）、弱 ETag 和本地文件指纹都不参与比较；修改时间未知时不算“更晚”。限制：

- 大小不变、ETag 无法比较（分片上传，以及由 OSS Transfer 复制的 128 MiB 及以上的对象）、源端修改时间又不更晚的变化，无法发现。
- 使用 SSE-KMS 或 SSE-C 加密的对象，ETag 不是内容的 MD5。如果两边都像 MD5 ETag 但不相同，这类对象每次都会被覆盖。
- 规则比较的是两个存储系统的时钟。首次复制后，目标端的修改时间是复制时间，因此之后源端的修改能被发现。
- 任务的所有执行节点都必须是 v4.1.42 或更高版本。在旧版执行节点上创建此类任务会提示 *执行节点 … 版本过旧，不支持“覆盖有变化的对象”，请先升级*，旧版执行节点也不能加入此类任务。

**增量迁移。** 源端持续变化时，先做一次全量迁移，再用相同的任务定义加 **覆盖有变化的对象**（或 **跳过同名对象或文件** 加 **修改时间晚于**）多轮执行，直到剩余变化很少；然后停写，执行最后一轮，并在切换前做[对象比对](#对象比对)。源端的删除不会同步到目标端。完整的切换步骤见[规划](planning.zh-CN.md)。

使用 **跳过同名对象或文件** 的任务结束后，如果有被跳过的对象，任务详情会显示提示，因为被跳过的对象可能是旧版本。对象存储之间的任务在提示中提供 **对象比对** 按钮，点击即可打开已填好参数的比对；`task show` 也会显示同样的提示。

### 迁移范围

| 选项 | 控制台 | CLI | 说明 |
| --- | --- | --- | --- |
| 整个存储桶 | 前缀留空 | （默认） | |
| 前缀 | 源前缀 | `--prefix` | 以该前缀开头的对象；空格和斜杠按原样保留 |

### 目标命名

| 规则 | CLI | 示例（源对象 `logs/2026/a.txt`） |
| --- | --- | --- |
| **保留原 Key**（默认） | `--mapping preserve` | `logs/2026/a.txt` |
| **添加目标前缀** | `--mapping add-prefix --target-prefix backup` | `backup/logs/2026/a.txt` |
| **替换源前缀**（需填写源前缀） | `--mapping replace-prefix --prefix logs/ --target-prefix archive/` | `archive/2026/a.txt` |
| **指定目标 Key**（单个对象） | `--mapping exact-key --object-key K --target-key T` | `T` |

**添加目标前缀** 在前缀末尾没有 `/` 时会补一个。**替换源前缀** 按字面替换，不会补 `/`，表示目录时请让两个前缀都以 `/` 结尾。上传使用 `--target-prefix` 或 `--target-key`；下载的目标是绑定的本地目录（单个对象可用 `--target-relative-path`）。

### 执行节点与分发方式

- **执行节点**（对象存储之间的任务用 `--node`，本地迁移用 `--binding 节点=路径`）：运行任务的执行节点。请选择靠近数据的节点，见[规划](planning.zh-CN.md)。
- **节点分发方式**（`--distribution`）：**均衡分发**（默认）把每个子任务分给剩余工作量（字节数加每个对象的固定开销）最少的所选节点。**亲和分发** 把所有子任务都分给第一个所选节点，其他节点只在它失联时接管其工作。上传任务由绑定的节点数决定。
- 任务存在期间可以增减执行节点（见[调整任务的执行节点](#调整任务的执行节点)）。

### 限速与并发

- **任务限速**（`--bandwidth-mbps`、`--list-qps`、`--head-qps`、`--put-qps`）：整个任务的总量，在其节点间分配，任务运行中可以修改（见[任务限速在节点间的分配](#任务限速在节点间的分配)）。LIST / GET 包括列举和所有对象读取。
- **节点限速** 和 **节点并发** 属于每个执行节点，对它上面的所有任务生效（见[节点限速](#节点限速)、[节点并发](#节点并发)）。
- **分段下载**（仅下载，`--ranged-download auto|off`）：对 128 MiB 及以上的对象并行读取多个区间（见[分段下载选项](#分段下载选项)）。

### 会复制哪些内容

迁移会复制对象内容、`Content-Type`、`Content-Encoding`、`Content-Disposition`、`Cache-Control` 和自定义元数据（`x-amz-meta-*`）。不会复制 ACL、存储类型、标签、对象锁设置和历史版本，目标端使用自己的设置和默认值。目标端的修改时间是复制的时间。128 MiB 及以上的对象以分片上传写入，分片大小为 8 MiB（1 GiB 起为 16 MiB，必要时更大，以保证不超过 10,000 个分片），因此其 ETag 与单次上传的 ETag 不同。

## 任务详情：需要关注与失败摘要

任务详情在统计数据上方显示需要关注的情况：

- **对象失败**：主要原因和对象数，例如 *全部 18 个对象失败：执行节点没有本地目录的读写权限*，最多再列出两个原因（*另有 N 个：…*），以及 *可在“异常记录”中查看失败对象并重试。* 摘要根据最多 1,000 条异常记录生成。
- **节点离线**（任务运行期间）：*执行节点 … 离线，任务等待其恢复连接*，并为每个节点显示 *… 最后连接于 …* 或 *… 尚未连接*。运行中任务的所有节点都离线时，显示这一项而不是失败摘要。

`oss-transfer-cli task show ID` 以 *需要关注* 一行显示同样的内容，`exceptions list` 显示每条记录的原因。API 在 `GET /api/master/tasks/{id}` 中以 `attention`、`failureSummary` 和 `offlineNodes` 返回。

## 任务报告

任务停止或结束后，在任务详情中点击 **导出任务报告**，或运行：

```sh
oss-transfer-cli task report ID --output task-ID.zip
```

ZIP 中包含：

| 文件 | 内容 |
| --- | --- |
| `task-summary.csv` | 每个任务一行，含各项计数 |
| `file-results.csv` | 每个对象一行：源、目标、节点、结果（`SUCCESS`、`SKIPPED`、`FAILED`、`UNPROCESSED`、`UNKNOWN`）、原因代码和错误信息 |
| `exception-details.csv` | 失败和结果未知的对象及其原因 |
| `report-metadata.json` | 报告是否完整、不完整的原因，以及用英文解释每个代码的 `reasonCodeMeaning` |

报告列出了任务发现的每个对象的最终结果时，即为 **完整**。CLI 会显示 *报告完整：是/否*、对象结果（*成功 N，跳过 N，失败 N，未处理 N，结果未知 N*），不完整时逐条列出原因，并以状态 3 退出（ZIP 仍会保存）：

| 代码 | 含义 | 处理方法 |
| --- | --- | --- |
| `SCAN_INCOMPLETE` | 源端对象尚未全部列举 | 继续任务，然后重新导出 |
| `TASK_STOPPED` | 任务已停止，还有对象没有迁移 | 继续任务，或接受部分结果 |
| `UNPROCESSED_OBJECTS` | 有对象尚未处理 | 重试或继续任务 |
| `NODE_REPORT_INCOMPLETE` | 部分对象的结果无法从执行节点读取，这些行为 `UNKNOWN` | 让提示中的节点恢复在线，然后重新导出 |
| `STATE_CHANGED_DURING_EXPORT` | 导出期间任务发生了变化 | 重新导出 |
| `COUNTS_DO_NOT_RECONCILE` | 报告中的对象数与任务统计不一致 | 重新导出；仍然如此时，保留报告以便排查 |
| `TASK_ERROR` | 任务记录了错误 | 查看 `exception-details.csv` |

`file-results.csv` 中的原因代码包括 `TRANSFER_FAILED`（见错误信息）、`DESTINATION_EXISTS`（按冲突策略跳过）、`SOURCE_DELETED`、`SOURCE_REFRESHED`、`NOT_COMPLETED` 和 `LEDGER_UNAVAILABLE`（无法从执行节点读取结果）。完整的报告只说明任务做了什么，并不证明内容一致；核对内容请使用[对象比对](#对象比对)。

`--output -` 把 ZIP 写到标准输出，例如从容器中取出报告：`docker compose exec master oss-transfer-cli task report 12 --output - > task-12.zip`。一次导出所有本地迁移的报告，使用 `exceptions export local --output 文件.zip`。

## 对象比对

在 **运维工具 → 对象比对** 中，为两侧分别选择单个对象或存储桶/前缀。前缀比对时，源前缀替换为目标前缀：`images/` 下的 `images/a.jpg` 对应 `backup/` 下的 `backup/a.jpg`。前缀为空表示整个存储桶。结果包括任一侧缺失的对象。

每个执行节点同一时间只执行一次比对。Master 在一个在线且没有比对在运行的执行节点上启动比对，优先选择已升级到本版本的执行节点；结果保存在该执行节点上。使用 CLI 时运行 `object compare`（见 [CLI](cli.zh-CN.md#比对存储的对象)）。

**元数据（不读取内容）** 模式对两侧的每个对象各发送一次 HEAD 请求，比较大小、`Content-Type`、`Content-Encoding`、`Content-Disposition`、`Cache-Control` 和自定义元数据，即迁移会保留的属性。它不读取对象内容，因此元数据一致不代表内容一致。修改时间和存储类型不参与比较；ETag 也不作为跨厂商通用的内容哈希：分片上传和不同的存储服务可能为相同内容生成不同的 ETag。ETag 只用于提示：其他属性都一致，而两端 ETag 都是普通 MD5 形式（32 位十六进制数字，不带分片上传的 `-N` 分片数）且不同时，结果为 *ETag 不同*（`ETAG_MISMATCH`），而不是 *一致*。这说明内容很可能不同，但并不确定：有些存储服务返回的 ETag 形似 MD5，却不是内容的 MD5，例如 Amazon S3 上用 SSE-KMS 或 SSE-C 加密的对象。请用内容比对确认这类对象。任一端的 ETag 来自分片上传时，不比较 ETag。

**内容 SHA-256（流式）** 模式同时读取两端的完整对象，比较大小和 SHA-256，不比较元数据；大小不同的对象不读取内容，直接判为不一致。它不生成本地对象文件，但会通过网络完整传输两端内容，可能产生存储读取费用。不超过 8 MiB 的对象，以及不支持字节区间读取的存储上的对象，用一个请求读取，最多尝试 3 次（分别在 1、2 秒后重试）。更大的对象按 8 MiB 区间读取；某个区间读取失败时，分别在 1、2、4 秒后最多再读 3 次。60 秒内没有收到任何数据的读取视为失败。读取完成后，再用 HEAD 请求检查两端对象；期间发生变化的对象标为 *比对期间已变化*。进度包括两端已读取的字节数，因此读取大对象时也能看到进展。

每个已比对的对象得到以下结果之一：

| 结果 | 控制台 | 含义 |
| --- | --- | --- |
| `MATCH` | *一致* | 只计数，不列出 |
| `DIFFERENT` | *不一致* | 两端都存在但不相同。该行列出不同的属性：元数据模式为 `size`、`contentType`、`contentEncoding`、`contentDisposition`、`cacheControl` 或 `metadata`；内容模式为 `size` 或 `sha256` |
| `ETAG_MISMATCH` | *ETag 不同* | 仅元数据模式：比较的属性都一致，但两端普通 MD5 形式的 ETag 不同。这只是提示：不是 MD5 的单段 ETag（例如 SSE-KMS 或 SSE-C 加密的对象）也可能被标出 |
| `MISSING_TARGET` | *目标缺失* | 只在源端存在；已用 HEAD 请求确认目标端没有该对象 |
| `EXTRA_TARGET` | *目标多余* | 只在目标端存在；已用 HEAD 请求确认源端没有该对象 |
| `CHANGED_DURING_COMPARE` | *比对期间已变化* | 比对该对象期间，任一端的对象发生变化、出现或消失；请稍后重新比对 |
| `ERROR` | *读取失败* | 某一端无法读取；该行给出原因（见[错误详情和日志](#错误详情和日志)） |
| `BOTH_MISSING` | *两端均不存在* | 单对象比对时，两端都没有该 Key |

除 `MATCH` 外，每种结果都作为一条差异保存。各项计数涵盖所有已比对的对象；列表中的“差异”指除 *一致* 以外的所有结果。

**速度。** 元数据模式下每个执行节点同时比对最多 32 个对象，内容模式下最多 8 个；两侧分别按每页 1,000 个 Key 列举。比对不受任务限速约束，但与该节点上的传输共用节点的请求上限和带宽上限（见[节点限速](#节点限速)），因此大型比对和繁忙的传输会互相拖慢。元数据模式下每个对象在两侧各需一次 HEAD 请求，按默认 2,800 次/秒的 HEAD 上限，每秒最多约比对 1,400 个对象；存储服务的延迟通常使实际速率更低。内容模式下两侧的读取都计入节点带宽上限，每个字节计两次：按默认的 2,000 Mbps，每秒最多约比对 125 MB 的对象。

### 查看结果

页面按开始时间倒序列出所有节点上的比对，显示状态、源端和目标端、方式、已检查的对象数、差异数、开始时间和节点。点击某个比对即可查看，页面地址中会保留其 ID（`?comparison=ID`）。有比对在运行时，列表每 5 秒刷新一次。无法连接的节点上的比对显示为 *节点不可用*，不显示计数，页面会提示有几个节点暂时无法连接；有节点不可用时，列表每 15 秒自动刷新一次，因此节点恢复后，这些比对会重新显示其状态。选择这样的比对时，页面提示其节点不可用并自动重试，每次等待的时间加倍，最长 60 秒。节点上已删除的比对，以及已从集群移除的节点上的比对，不再列出；打开这样的比对时，页面提示比对已不存在。使用原数据目录重新注册的节点保留其比对。本版本的执行节点上报了 Master 不知道的比对时（例如 Master 的数据库恢复之后），这些比对会重新列出，可以照常查看、取消和删除。

<p align="center"><img src="images/comparison.zh-CN.png" width="720" alt="对象比对结果，红框标出按结果筛选和导出全部差异按钮"></p>

比对运行期间，页面显示已检查的对象数、每秒比对的对象数和已用时间，内容模式还显示已读取的字节数。已用时间只计算比对实际运行的时间。各项计数同时也是筛选条件：选择 *全部差异* 或某一种结果，只列出对应的行；*已检查* 和 *一致* 只显示数量。每行显示源端和目标端 Key、结果（附不同的属性，或错误及其详情）、两端大小，内容模式还显示两端的 SHA-256。每页 100 行，用 **上一页** 和 **下一页** 翻页；比对运行期间，当前页每 1.5 秒刷新一次，位置保持不变。所选结果在长列表中很少时，页面会自动往后多查找几页；仍未找到时，点击 **继续查找** 接着查找。

**取消比对** 停止正在运行的比对；已取消的前缀比对之后可以继续（见[继续比对](#继续比对)）。**删除比对结果** 删除未在运行的比对；运行中的比对需先取消。比对已被删除时（例如按保留规则清理），页面会提示结果不存在，并停止刷新。比对的结果文件已不在节点上时（例如被手动删除），比对保留其计数和状态，但页面不列出任何结果行，并显示 *该节点上的比对结果已不可用*；这种比对无法继续。

对应的 API：`GET /api/master/comparisons` 列出比对；有节点未响应时，`complete` 为 `false`，`unavailableNodes` 列出这些节点，这些节点上的比对状态为 `UNAVAILABLE`。`GET /api/master/comparisons/{id}?after=0&limit=1000&status=DIFFERENT,MISSING_TARGET` 返回比对及一页结果行：`limit` 为 1–1,000（默认 50），`status` 可以省略。用返回的 `nextAfter` 作为下一次请求的 `after` 继续读取，最后一页没有 `nextAfter`。离线节点上的比对立即返回 HTTP 503 *节点离线*；已不存在的比对（包括已从集群移除的节点上的比对）返回 HTTP 404 *比对记录不存在*。取消、删除、导出和继续也是如此，只是删除已移除节点上的比对会成功，并且只是把它从列表中移除。筛选后的一页可能少于 `limit` 行，甚至为空，但仍可能带有 `nextAfter`。除比对设置外，比对记录还包含各项计数 `compared`、`matched`、`different`、`etagMismatch`、`missing`、`extra`、`changed`、`errors` 和 `bothMissing`，已保存的结果行数 `rows`，以及 `rowsTruncated`、`truncatedReason`、`lastStoredKey`、`checkpoint`、`resumable`、`bytesRead`、`elapsedMillis`、`error` 和 `errorDetail`。

### 导出结果

在控制台点击 **导出 ZIP**，或在 CLI 中运行 `object export`（见 [CLI](cli.zh-CN.md#比对存储的对象)），下载一个 ZIP 文件（控制台下载的文件名为 `comparison-ID.zip`），其中包含三个文件：

| 文件 | 内容 |
| --- | --- |
| `differences.csv` | 按 Key 顺序排列的已保存结果行，列为 `number`、`key`、`status`、`sourceKey`、`destinationKey`、`sourceSize`、`destinationSize`、`sourceSha256`、`destinationSha256`、`reasons`（以 `;` 分隔）、`error` 和 `errorDetail`。指定结果筛选（CLI 的 `--status`，API 的 `status`）时只包含这些结果 |
| `retry-source-keys.incr` | 所有 `MISSING_TARGET`、`DIFFERENT` 和 `ETAG_MISMATCH` 行的源端 Key，每行一个，不受结果筛选影响 |
| `summary.json` | 比对本身（ID、节点、状态、方式、范围、源和目标）、各项计数、`storedRows`、`exportedRows`、`statusFilter`、`complete` 和 `incompleteReasons`、`truncatedReason` 和 `lastStoredKey`、`retryStatuses`、`retryKeys`、`retryKeysOmitted`、`retryPrefixesMatch`、`csvEscaping`，以及开始、结束和导出时间 |

只有比对已完成、其结果在节点上可用、保存了全部差异，并且文件包含全部已保存的结果行（指定结果筛选时，为这些结果的全部已保存行），`complete` 才为 `true`；否则 `incompleteReasons` 列出每一项原因：`NOT_COMPLETED:<状态>`、`ROWS_TRUNCATED:<原因>`、`RESULTS_UNAVAILABLE`（节点上已没有结果文件）、`ROW_COUNT_MISMATCH` 或 `RETRY_KEYS_MISMATCH`。对于保存了全部差异的结果，导出还会与各项计数核对：筛选导出的行数必须等于所选结果的计数之和（`DIFFERENT` 对应 `different`，`ETAG_MISMATCH` 对应 `etagMismatch`，`MISSING_TARGET` 对应 `missing`，`EXTRA_TARGET` 对应 `extra`，`CHANGED_DURING_COMPARE` 对应 `changed`，`ERROR` 对应 `errors`，`BOTH_MISSING` 对应 `bothMissing`），否则为 `ROW_COUNT_MISMATCH`；`retryKeys` 加 `retryKeysOmitted` 必须等于 `missing` + `different` + `etagMismatch`，否则为 `RETRY_KEYS_MISMATCH`。这些计数核对不适用于[旧版执行节点](#旧版执行节点) 的结果，旧版执行节点把 `BOTH_MISSING` 计入错误数。运行中的比对也可以导出，此时文件包含已保存的结果行，并标为不完整。下载过程中，结果行逐页从节点读取；节点停止响应时下载失败，而不会得到一个被截短的文件。CLI 还可以导出 JSON Lines（`--format jsonl`）：每行一条已保存的结果，格式与 API 相同，筛选方式与 CSV 文件相同，不含汇总。

**CSV 转义。** CSV 文件使用 UTF-8 编码和标准的引号规则。为避免电子表格程序把 Key 当作公式执行，以 `=`、`+`、`-`、`@`、`'`、制表符、CR 或 LF 开头的值前面会加一个单引号（`'`）。要还原原值，凡以单引号开头的值，去掉开头的一个单引号即可。含 CR 或 LF 的值会加引号，其字节保持不变；有些 CSV 读取程序（例如 Go 的 `encoding/csv`）会把值中的 CR LF 转换为 LF。`retry-source-keys.incr` 和 JSON Lines 中的 Key 保持原样；需要每个 Key 都完全准确时，请使用 JSON Lines 导出（`object export --format jsonl`）。

**重新迁移列出的对象。** `retry-source-keys.incr` 是供 `import-inventory` 使用的 Key 清单（见 `oss-transfer-cli help tools`）。`import-inventory` 创建的任务把清单中的每个 Key 从源存储桶复制到目标存储桶中的同名 Key，因此只有比对的源前缀和目标前缀相同（`retryPrefixesMatch` 为 `true`）时才适用；前缀不同时，对象会写到源端 Key 下，请改用替换前缀的迁移任务。把该文件放进单独的目录，并加上 `--overwrite`：不加时，任务会跳过目标端已存在的对象，所有 `DIFFERENT` 和 `ETAG_MISMATCH` 的 Key 都属于这种情况。如果内容比对已确认 `ETAG_MISMATCH` 的对象相同，请先从清单中删除这些 Key。

```sh
mkdir retry && unzip comparison-ID.zip retry-source-keys.incr -d retry
oss-transfer-cli import-inventory source/photos target/archive retry --overwrite
```

清单不包含 `import-inventory` 无法读取的 Key：超过 1,024 字节、不是有效的 UTF-8、含 NUL、CR 或 LF，或者只有空白字符。`retryKeysOmitted` 统计这些 Key 的数量，可在 JSON Lines 导出（`object export --format jsonl`）中找到它们的准确值。`import-inventory` 每个文件最多接受 1000 万个 Key 或 1 GiB 的 Key；清单更长时，拆成同一目录下的多个 `.incr` 文件，每个文件生成一个任务。

对应的 API：带 Bearer 令牌请求 `GET /api/master/comparisons/{id}/export?format=zip&status=DIFFERENT`；`format` 为 `zip`（默认）或 `jsonl`。

### 继续比对

前缀比对大约每秒记录一次检查点：到该 Key 为止的所有对象都已比对并计数。比对期间执行节点重启或升级时，只要该节点的存储连接自比对开始或上次继续以来没有变化，执行节点重新运行后比对就会从检查点自动继续。集群中任何一个存储连接的任何变化都算作变化，因为 Master 会把每个连接同步到每个节点。否则比对保持 *比对已中断*，错误详情为 `storage connections changed; resume manually`；手动继续该比对后，自动继续会重新生效。

在控制台点击 **继续比对**，或在 CLI 中运行 `object resume ID`，可以继续已中断、失败或已取消的前缀比对，例如在修复存储访问之后；因此取消比对也可以当作暂停。比对仍在保存其结果的节点上运行，该节点必须在线且没有其他比对在运行；比对使用当前的存储连接设置，请确认它们仍指向原来的存储桶。两侧从检查点 Key 之后重新列举。各项计数和已保存的差异接着累计，不会重复计数或遗漏对象，已用时间也会累加。中断时正在比对的对象（例如内容模式下正在读取的大对象）会从头重新比对。正在取消的比对无法继续（*该比对无法继续*），请等它停止后再继续。对应的 API 是 `POST /api/master/comparisons/{id}/resume`。

继续后的比对同样不是快照：比对停止期间，检查点之前的位置上发生的变化不会被发现。单对象比对、无法保存结果的比对，以及 4.1.40 及更早版本的执行节点上的比对无法继续，请重新开始比对。

### 错误详情和日志

无法读取的行显示为 *读取失败*，附一条固定的提示和错误详情。详情说明是哪一端、哪种请求、HTTP 状态码、存储服务的错误码，以及可提供给存储服务商的请求 ID，例如 `target HEAD: HTTP 403 AccessDenied (request ID 1A2B3C)`。详情中不会包含凭证、签名、URL 或主机名。

LIST 请求因 HTTP 5xx 或 429、`SlowDown` 等限流错误码、网络错误或超时（每次尝试 3 分钟）失败时，最多重试 5 次，分别在 1、2、4、8、16 秒后进行。`AccessDenied`（HTTP 403）、`NoSuchBucket`（HTTP 404）或 `InvalidAccessKeyId` 等错误会立即失败。每个 HEAD 请求（含重试）最长 2 分钟。

列举请求重试后仍然失败，或存储返回的 Key 顺序不对时，比对失败。页面显示 *比对未能完成，请检查存储访问后重试。* 和错误详情，例如 `source LIST: HTTP 403 AccessDenied (request ID 1A2B3C)` 或 `source listing is not in ascending byte order after key "…"`；执行节点同时把 `comparison <ID> failed: <详情>` 写入其服务日志（Linux 上为 `/opt/oss-transfer/agent/data/logs/service.log`）。排除原因后继续比对即可，比对会从已比对的最后一个 Key 之后继续。执行节点无法写入结果时，比对失败并显示 *无法保存比对结果*；这种比对无法继续，请重新开始。

### 结果的保存和清理

结果保存在执行比对的执行节点上，位于其数据目录下的 `comparisons` 中（即 `service.json` 中的 `dataDirectory`；Linux 上为 `/opt/oss-transfer/agent/data/comparisons`），每次比对一个子目录。结果不写入 `agent.db`，不会让数据库变大，数据库备份和压缩也不包含它们（见[数据库维护](database-maintenance.zh-CN.md#比对结果)）。Key 长约 40 字节时，每条差异约占 260 字节，2 GiB 约可保存 800 万条差异；Key 更长，或内容模式的结果带有 SHA-256 值时，占用更多。

结果按以下规则自动删除，但正在运行的比对的结果不会被删除：

- 比对结束 30 天后删除；
- 节点上所有比对的结果合计超过 2 GiB 时，从最早结束的比对开始删除；
- 节点上的比对超过 500 个时，从最早结束的比对开始删除。

执行节点启动时、每次比对结束时以及每小时都会执行这些规则，因此比对运行期间，合计大小可能暂时超过预算，直到下一次检查删除较早的结果。**删除比对结果** 或 `object delete` 会立即移除比对；其文件在后台删除，执行节点重启后继续删除。

以下情况下，比对停止保存差异，但仍继续比对和计数：该比对自身的差异将超过整个预算（`STORAGE_BUDGET`）；或者写入差异后，数据目录所在磁盘的剩余空间将不足 1 GiB（`LOW_DISK_SPACE`）。比对页面随即显示原因和最后保存的 Key：到该 Key 为止的结果行是完整的，之后的差异只计数。提高预算或释放磁盘空间后重新比对，或用更小的前缀比对剩余的 Key。第三种原因 `LEGACY_LIMIT` 表示结果来自[旧版执行节点](#旧版执行节点)，最多只保存 10,000 条差异。

**配置文件。** 要修改上述限制，在执行节点的 `service.json` 中添加 `comparison` 对象，然后重启执行节点。省略或设为 0 的键保持默认值：

| 键 | 默认值 | 作用 |
| --- | --- | --- |
| `budgetBytes` | 2147483648（2 GiB） | 节点上已保存差异的总大小，也是单个比对最多保存的大小；至少 67108864（64 MiB） |
| `retentionDays` | 30 | 比对结束后保留的天数；最多 3,650 |
| `minimumFreeBytes` | 1073741824（1 GiB） | 保存差异时，数据目录所在磁盘至少保留的剩余空间 |

例如，要保留最多 10 GiB 的差异并保存 90 天，把该对象加到现有的 JSON 对象中，并保留其他键：

```json
"comparison": {
  "budgetBytes": 10737418240,
  "retentionDays": 90
}
```

调低预算或保留天数后，执行节点启动时会删除较早的结果。存在未知的键或超出范围的值时，执行节点无法启动；Master 的 `service.json` 中出现 `comparison` 对象时，Master 会拒绝该配置。重启前请用 `--check-config` 检查文件，方法同[调整自动降速参数](#调整自动降速参数)。500 个比对的上限是固定的。用 Docker 安装的执行节点没有 `service.json`，使用默认值。

### 旧版执行节点

4.1.40 及更早版本的执行节点在升级前保持原来的行为：逐个比对对象；每次比对只保存前 10,000 条差异（页面会提示该节点的版本最多保存这么多条）；只保留最近 10 次比对，开始新的比对时删除最早的一次。它们不提供 ETag 提示和错误详情；对于列举时间精确到毫秒的存储，它们会把几乎所有对象都标为 *比对期间已变化*。执行节点重启或升级会彻底结束其正在运行的比对。Master 可以列出、筛选和导出它们保存的结果行，但导出无法超出这 10,000 行；继续比对会被拒绝，并提示需要先升级该节点。新的比对优先分配给已升级的执行节点。

请升级这些执行节点（见[版本更新](#版本更新)）。执行节点升级前保留的比对仍可读取，按每条差异 512 字节计入预算，并按相同的规则删除。

### 限制

- 比对不是某一时刻的快照：每个对象在轮到它时才比对。需要验证某一固定数据集时，应先停止写入。
- 只能比对 S3 兼容的对象存储，不支持本地目录。
- 列举结果必须按 Key 的字节顺序升序返回，这也是 S3 的要求。按其他顺序列举的存储会导致比对失败，错误详情会给出顺序出错之前的那个 Key。
- 去掉各自的前缀后，Key 按字节逐一匹配，不忽略大小写，不做 Unicode 规范化，也不整理斜杠。

### 验收大规模迁移

一次比对只在一个执行节点上运行，每个执行节点同一时间只运行一次比对。按默认限速，元数据比对每秒最多检查约 1,400 个对象，1 亿个对象在一个执行节点上约需 20 小时；内容比对要读取两端的全部数据，速度慢得多，费用也高得多。验收大规模迁移时：

1. 按前缀拆分存储桶（例如按顶层目录），每个前缀启动一次比对。Master 会把每次新比对分给一个在线且没有在运行比对的执行节点，因此多个前缀可以在多个执行节点上并行。
2. 用元数据模式比对全部对象；再用内容模式抽查部分前缀，或核对 ETag 不同（`ETAG_MISMATCH`）的对象。
3. 在迁移完成或空闲时运行比对：比对与迁移共用节点限速。
4. 导出每次比对的结果，必要时重新传输列出的对象（见[导出结果](#导出结果)），然后对这些前缀再比对一次。

每个执行节点默认最多保存 2 GiB 的差异（见[结果的保存和清理](#结果的保存和清理)）。[规划](planning.zh-CN.md)把比对纳入了切换步骤。

## 监控与日志

OSS Transfer 没有内置告警。可以手动或用脚本关注以下几项：

| 关注点 | 方法 |
| --- | --- |
| Master 是否运行 | `curl -fsS http://MASTER:1685/healthz` 返回 `{"role":"master","success":true}`（无需登录） |
| 执行节点是否在线 | **执行节点** 页面，或 `oss-transfer-cli node list` |
| 失败或部分失败的任务 | `oss-transfer-cli task list --status FAILED` 和 `--status PARTIAL_FAILED` |
| 对象失败的原因 | 任务的“需要关注”提示（见[任务详情](#任务详情需要关注与失败摘要)）、**异常记录**、`exceptions list failed --task-id ID` |
| 限流 | 节点限速被自动降低时控制台显示的横幅；`limit list` 和 `limit history`（见[存储限流](#存储限流)） |
| 磁盘空间 | Master 和执行节点的数据目录，以及下载目标目录 |

CLI 适合在脚本中使用：加 `--json` 得到机器可读的输出，并检查退出状态（0 成功，1 失败，3 结果不完整；见 [CLI](cli.zh-CN.md#输出语言和退出码)）。例如在 Master 主机上用 cron 列出离线的执行节点：

```sh
oss-transfer-cli --json node list | jq -r '.data.nodes[] | select(.agent and (.online | not)) | .address'
```

**日志。** 每个服务把日志写入其数据目录下的 `logs/service.log`（Linux 上为 `/opt/oss-transfer/master/data/logs/service.log` 和 `/opt/oss-transfer/agent/data/logs/service.log`）。systemd 只记录启动、停止和退出状态（`journalctl -u oss-transfer-master`）。服务不会自行轮转日志，请使用 `logrotate` 的 `copytruncate`，见[日志](install.zh-CN.md#日志)。Docker 部署使用 `docker compose logs` 或 `docker logs`。

值得搜索的日志内容：`Service failed:`（服务因错误停止）、`comparison … failed:`（比对停止），以及安装脚本输出中的 `Startup failed` 或 `启动失败`。执行节点的日志还记录每个子任务尝试的开始和结束（`task #12-3 (child …): attempt 1 ended PARTIAL_FAILED: 120 succeeded, 0 skipped, 5 failed of 125 objects`）、每次尝试中前 20 个失败对象的 Key 和原因（`object "…" failed:`）、存储请求重试（`storage request PutObject on bucket …: attempt 2 of 10 failed (transient failure), retrying:`，最多每 30 秒一行），以及与 Master 连接的变化（`Connection to the Master at … lost`、`… restored after 45s`）。请求 URL 不含查询参数；日志从不记录凭据。

## 备份与恢复

Master 的数据库保存账号、存储连接（加密存储）、任务及其进度。每个执行节点的数据库保存它的身份、它负责的那部分任务及结果；比对结果是数据库旁边的文件。已迁移的对象和文件不在两者之中。

备份需要在服务停止时进行，不支持在线备份。服务重新启动后，运行中的任务会继续。

**备份** 原生安装，以 Linux 上的 Master 为例：

1. 停止服务：`sudo systemctl stop oss-transfer-master`。
2. 复制完整的 `config` 和 `data` 目录，包括密钥文件（`master.db.key` 或 `agent.db.key`）：`sudo tar -czf master-backup.tgz -C /opt/oss-transfer/master config data`。
3. 启动服务：`sudo systemctl start oss-transfer-master`。
4. 把备份保存在安全的地方。其中包含数据库密钥，能读取它的人就能解密存储凭据。

需要保留执行节点上的任务结果时，按同样方法备份执行节点（把 `master` 换成 `agent`）；执行节点也可以直接用新节点替换。

**恢复** 到同一台主机，或使用相同路径的新主机：

1. 安装相同版本（使用 `--version`，见[安装](install.zh-CN.md#安装指定版本或预发布版本)），或保留现有安装，然后停止服务。
2. 用备份替换 `config` 和 `data` 目录：`sudo tar -xzf master-backup.tgz -C /opt/oss-transfer/master`。
3. 如有需要，用相同的角色和 `--root-dir` 重新运行安装脚本修复服务定义（见[重装且不丢失数据](install.zh-CN.md#重装且不丢失数据)），或直接启动服务。
4. 登录并检查任务和节点。

执行节点会连接它加入时使用的 Master 地址。请把 Master 恢复到该地址所指向的位置（迁移 IP 地址或域名），否则执行节点无法重新连接。

Docker 部署的全部数据都在其数据卷或数据目录中，见 [Docker Compose](docker-compose.zh-CN.md)。安装脚本在升级时自动做的备份，见[从失败的升级中恢复](#从失败的升级中恢复)。

## 版本更新

先更新 Master，再更新执行节点。尽量等活动任务完成后再更新。

1. 打开 **运维工具 → 版本更新**。Master 卡片显示当前版本和最新正式版。点击 **更新 Master**，Master 会安装该最新正式版并短暂重启。
2. 打开 **执行节点 → 版本更新**，点击 **更新全部节点**。执行节点逐台更新到 Master 的版本：前一台以新版本重新连接后，才更新下一台；失败时停止队列。队列保存在 Master，关闭页面或重启 Master 都不会丢失。也可以单独更新某个节点。

使用 CLI：

```sh
oss-transfer-cli update check
oss-transfer-cli update master --yes
oss-transfer-cli update agents --all --yes
oss-transfer-cli update status --watch 5
```

`update check` 显示 *当前版本 v4.1.41 → 可升级到 v4.1.42* 和发布说明链接，或说明已是最新正式版。`update master` 会自行检查并安装最新正式版；Master 已是最新版本时会说明并以状态 0 退出。请求被接受不代表更新已完成，请用 `update status` 跟踪。

**无法在线更新的节点。** 此时 **更新** 按钮不可用，鼠标悬停会显示原因；`update status` 也显示同样的原因。常见原因和处理方法：

| 原因 | 处理方法 |
| --- | --- |
| 节点离线 | 让它恢复在线，重新连接后即可更新 |
| 节点运行在容器（Docker）中 | 使用 **更新命令**（见下文） |
| 服务需要以 root 身份（Windows 为管理员权限）运行才能在线更新 | 用安装脚本升级：`install.sh --upgrade`，或 `Install.ps1 -Upgrade` |
| 未找到安装记录，或安装记录不一致 | 先用安装脚本升级一次（`install.sh --upgrade`） |
| 安装记录中的 CLI 缺失 | 用 `install.sh --upgrade --force` 修复 |
| 已与 Master 版本一致 | 无需操作 |

主机上的问题（例如服务账号）修正后，一分钟内会重新检查，无需重启服务。

**Docker 执行节点。** 容器中的执行节点无法替换自己。它所在的行有 **更新命令** 按钮，点击后打开 *更新 Docker 执行节点 名称*，列出需要在其主机上复制运行的命令。执行节点已与 Master 版本一致时，按钮为 **重建命令**（打开 *重建 Docker 执行节点 名称*），命令相同，可用于添加目录挂载等：

- 用 `docker run` 启动的执行节点：`docker pull 镜像`、`docker rm -f 名称`，然后用 `docker run -d …` 从数据卷 `名称-data` 重新启动它。创建容器时加过的其他参数（例如目录挂载）请一并保留；
- 用安装脚本的 Docker Compose 方式安装的执行节点：先把 `/opt/oss-transfer-compose/agent/docker-compose.yml` 中的 `image` 改为新镜像，再运行 `docker compose -p oss-transfer-agent -f /opt/oss-transfer-compose/agent/docker-compose.yml pull` 和 `… up -d`。

节点身份和设置会保留；正在执行的子任务会在节点重新连接后继续。Docker Compose 部署的 Master 通过拉取新镜像更新（见 [Docker Compose](docker-compose.zh-CN.md)）。

### 在线更新的过程

需要带任务升级时，先更新 Master，再逐台更新执行节点。原生安装脚本在停止执行节点之前，会请 Master 暂时保留该执行节点的任务；新服务通过验收或成功回滚后解除保留，安装脚本无法完成时最多保留 30 分钟。旧版 Master 需要先升级，执行节点的安装脚本才能使用这项保护。

Master 和每个执行节点上的更新程序各自从 GitHub 或京东云 OSS 镜像下载发布安装包，并在停止服务前完成下载和校验；无法联网的主机请改用[离线安装](offline-install.zh-CN.md#升级和重装)中的升级步骤。随后，更新程序由独立进程运行原生安装脚本。安装脚本临时备份程序、配置、服务定义和已停止的数据库；新服务通过健康检查并确认安装后，删除本次备份。启动失败时，尝试恢复旧安装并保留恢复文件。执行节点重启导致中断的传输会在重新连接后继续；正在运行的比对如何继续，见[继续比对](#继续比对)。

在 Linux 上，更新在名为 `oss-transfer-update-…` 的临时 systemd 单元中运行，systemd 219 同样适用。systemd 低于 236 时，更新失败后该单元会一直显示为失败状态，执行 `systemctl reset-failed` 即可清除。systemd 低于 240 时，无法报告更新辅助程序启动失败；这类更新要在一小时没有进展后才显示为失败。

备份写入本机的[默认备份目录](install.zh-CN.md#路径和端口)，即使早期安装保存过共享存储路径也不再沿用。需要其他位置时，显式传入 `--backup-dir`，PowerShell 使用 `-BackupDir`。停止服务前，安装脚本会清理符合条件的旧备份并检查可用空间。**升级备份 → 清理备份** 删除成功升级留下的备份；失败的备份和缺少完成标记的旧备份继续保留。数据库备份每 10 秒显示一次进度，包括最后的落盘同步。

如果计划降级，升级前应另行备份各服务的程序、配置和已停止的数据库（见[备份与恢复](#备份与恢复)）；成功升级后不会留下回退副本。把 Master 降级到按需分配任务限速之前的版本时，运行中的任务可能短暂超出限速，见[任务限速在节点间的分配](#任务限速在节点间的分配)。自动回滚未完成时，见[手动恢复](#从失败的升级中恢复)。

在线更新只安装最新正式版。需要安装其他版本时，在该主机上带 `--version` 运行安装脚本（见[安装](install.zh-CN.md#安装指定版本或预发布版本)）；`update master --version X` 指定其他正式版时会被拒绝。从尚不支持在线更新的版本首次升级时，同样使用安装脚本。在运行中的容器内替换程序，会在重建容器时丢失。

### 升级到 v4.1.42

- **执行节点也要更新。** v4.1.42 的多项功能在执行节点上实现：自动寻址和存储桶级连接检查、**覆盖有变化的对象**、应对存储中断的更长重试、跳过源端已删除的对象，以及下载写入探测。执行节点版本较旧时，Master 会退回原来的行为。
- **现有连接的寻址方式。** 从未选择过寻址方式的连接，在其执行节点升级到 v4.1.42 后改用自动寻址：带端口、使用 IP 地址或本地主机名的 Endpoint 会变为 Path-style。这正是自建存储所需要的；如果你的服务需要 Virtual-hosted，请明确选择。
- **被移除的执行节点会停止。** 在 Master 上移除的执行节点现在会停止，而不是每 5 秒重启一次。现有的 systemd 单元会在下次升级时加入 `RestartPreventExitStatus=78`。
- **任务报告。** 停止后继续过、或重试过失败对象的任务，其报告重新变得完整。该修复在 Master 上，旧版执行节点同样适用。
- **CLI 退出码。** 在连接 Master 之前发现的命令行错误现在统一以 2 退出（以前部分为 1），401 和 403 总是以 1 退出。请检查依赖退出码的脚本（见 [CLI](cli.zh-CN.md#输出语言和退出码)）。
- **密码** 至少需要 8 个字符，不能是常见或容易猜到的密码（见[安全](security.zh-CN.md)），且不能与用户名或当前密码相同。

### 试用预发布版本

检测更新只提供最新正式版。`4.1.29-beta.1`、`4.1.29-rc.1` 这类预发布版本不会被自动提供；除非你主动选择，正式版安装永远不会被更新到预发布版本。版本按 [SemVer](https://semver.org/lang/zh-CN/) 优先级排序：`4.1.29-beta.1` < `4.1.29-beta.2` < `4.1.29-rc.1` < `4.1.29`。

在托管的原生 Master 上安装预发布版本：

1. 带上预发布参数打开版本更新页面：`/tools?tab=updates&channel=prerelease`。Master 卡片上会出现 **指定版本** 控件；没有该参数时不显示。
2. 输入精确的版本号，例如 `4.1.29-beta.1`，点击 **安装指定版本**。
3. 确认警告。预发布版本是实验性构建，正常更新不会提供。

使用 CLI 时运行 `oss-transfer-cli update master --version 4.1.29-beta.1 --allow-prerelease --yes`。不加 `--allow-prerelease` 时，预发布版本会作为参数错误被拒绝（退出码 2）。对应的 API 是 `POST /api/master/software-updates/master`，请求体为 `{"version": "4.1.29-beta.1", "allowPrerelease": true}`；不带该字段时，Master 拒绝预发布版本。

Master 先确认该版本确实已发布：GitHub 读取 `releases/tags/vX.Y.Z-…`，只有在指定了该标志时才接受预发布标记（草稿一律拒绝）；京东云 OSS 镜像读取版本目录，而不是 `latest/`。下载过程使用与正式版相同的安装包摘要、SHA-256 和版本校验，目标版本也必须比当前版本新。

**执行节点。** Master 运行预发布版本后，**更新全部节点**（或 `update agents --all --yes`）会把执行节点更新到与 Master 完全相同的版本；选择 Master 自身的版本即视为明确同意。执行节点需要运行支持预发布更新的版本（引入此功能的版本或更新版本）；旧版执行节点会被跳过并给出说明，请先用安装脚本更新一次。Master 运行正式版期间，不会向执行节点提供或下发预发布版本。

**回到正式版。** 发布了比当前预发布版本更新的正式版后（例如 `4.1.29-beta.2` 之后的 `4.1.29`），正常检测更新就会提供它，按常规先更新 Master 再更新执行节点即可。从预发布版本回到更早的正式版（例如 `4.1.28`）属于降级：在线更新会拒绝，而且数据库可能已经使用更新的格式。如果之后可能需要回退，请在安装预发布版本之前另行备份。

Docker Compose 部署通过 `OSS_TRANSFER_IMAGE=moonwx/osstransfer:4.1.29-beta.1` 选择预发布版本，见[安装指定版本](install.zh-CN.md#安装指定版本或预发布版本)。此功能之前发布的 Master 会拒绝 `allowPrerelease` 字段。

### 从失败的升级中恢复

使用安装器打印的备份目录。停止受影响的服务，然后用一个能同时读取当前和备份数据库格式的 Master 或执行节点程序运行 `--config <备份目录>/service.json --restore-state <备份目录>/database`。快照旁有 `database.key` 时一并保留。该命令把数据库恢复到所保存配置中记录的数据目录。如果已安装的数据库丢失了密钥，先从同一数据库的备份中恢复对应的 `master.db.key` 或 `agent.db.key`。

把保存的程序、配置、安装元数据、服务定义和 CLI 恢复到原来的位置，然后启动服务。已迁移的文件保持原样。自行备份的方法见[备份与恢复](#备份与恢复)；计划降级时，保留对应版本的程序。

## 移除执行节点

不再需要或要替换某个执行节点时：

1. 先停止或完成使用它的任务，或把任务移到其他节点（见[调整任务的执行节点](#调整任务的执行节点)）。有未结束的任务使用该执行节点时，Master 会拒绝移除；已完成和已停止的任务不影响移除。
2. 导出需要保留的内容。[任务报告](#任务报告)中逐个对象的结果和[对象比对](#导出结果)结果保存在执行节点上。执行节点移除后，保存在它上面的这些结果将无法再获取：之后导出的任务报告不完整（该节点上的对象结果为 `UNKNOWN`），它的比对记录也会从比对历史中消失。请先保存任务报告（`oss-transfer-cli task report ID`）和比对结果（`oss-transfer-cli object export ID`）。移除对话框和不带 `--yes` 的 `agent remove` 也会给出这条提醒。
3. 在 **执行节点** 页面点击 **移除节点**，或运行 `oss-transfer-cli agent remove 节点 --yes`。CLI 会确认：*已移除执行节点 节点。该主机上的 Agent 服务会自行停止且不再重启；如需删除其程序和数据，请在该主机运行安装脚本并加 --uninstall --role agent*。
4. 在该主机上[卸载](install.zh-CN.md#卸载)它，或让它保持停止状态。

被移除的执行节点会在服务日志中写入 *Service failed: agent enrollment was revoked by the Master. This Agent was removed from the cluster or its enrollment was revoked on the Master, so the service has stopped and will not restart automatically …*，然后退出：

- Linux：`systemctl status oss-transfer-agent` 显示 `failed` 和 `status=78`，systemd 不会重启它。
- Windows：退出状态为 78，服务保持停止。
- macOS：退出状态为 0，因此 launchd 不会重启它。
- FreeBSD：其 `daemon(8)` 监护进程会被停止。
- Docker 镜像：容器记录原因后保持空闲，直到你停止它；请删除容器和数据卷（见[卸载](install.zh-CN.md#用控制台-docker-指令启动的执行节点)）。

要重新使用这台主机，从 **执行节点 → 添加节点** 复制新的加入命令运行即可。

## 执行机制

以下各节详细说明执行节点怎样分担和限制工作。调优大规模迁移，或需要理解控制台中某个不寻常的读数时，可以参考。

### 节点并发

在 **执行节点 → 编辑节点** 中可调整 **子任务并发** 和 **每个子任务的对象并发**。默认值分别是 32 和 4，即单节点最多同时传输 128 个对象；已有配置继续保留。使用 CLI 时运行 `node update <节点> --child-concurrency 32 --object-concurrency 4`（见 [CLI](cli.zh-CN.md#添加和移除执行节点)）。

保存后直接作用于正在运行的工作，重启后保留。调低并发时，已发出的请求会先完成，再按新上限继续调度。网络未充分利用时，调高并发可能有帮助；节点和任务的带宽、QPS 限制仍然生效。子任务并发范围为 1–256，对象并发为 1–64，两者乘积不能超过 1024。空闲的对象并发还能让大对象同时拉取更多区间（见[大对象](#大对象)）。

### 节点限速

任务的请求同时受两类限速约束。节点限速属于单个执行节点，由该节点上运行的所有任务共用；任务限速是单个任务的总量，在它的执行节点之间分配（见[任务限速在节点间的分配](#任务限速在节点间的分配)）。只有两者都允许时，请求才会发出；不属于任务的请求（例如对象比对）只受节点限速约束。存储服务限流时，执行节点会暂时降低自己的节点请求上限（见[存储限流](#存储限流)）；任务限速不会被自动修改。

每个执行节点有四项节点限速：

| 限速 | 默认值 | 适用范围 |
| --- | --- | --- |
| LIST | 100 次/秒 | 列举对象（ListObjects、ListBuckets） |
| PUT | 1,400 次/秒 | 上传（PutObject、UploadPart、CreateMultipartUpload、CompleteMultipartUpload） |
| HEAD | 2,800 次/秒 | 读取对象元数据（HeadObject） |
| 带宽 | 2,000 Mbps | 从源端读取的数据，包括大对象的每个区间 |

对象 GET（包括大对象的区间读取）没有节点请求上限：它们受节点带宽约束，速率则由任务的 LIST / GET 限速控制。列举分片（ListParts）和中止分片上传也不受节点限速约束。每次重试都按一个新请求计数。

**修改节点限速。** 打开 **执行节点**，在 **实时状态** 中，每个节点卡片的 **请求与带宽** 区域为每项限速显示一行。点击某一行的 **调整**，修改该节点的这项限速；或点击页面顶部的 **调整限速**，把同一个值应用到全部节点（**应用范围** 选 **全部执行节点**），此时每个节点都使用这个值，而不是分摊它。请求上限以次/秒为单位，带宽以 Mbps 为单位，0 表示不限速。Master 接受 0.01–1,000,000 次/秒，带宽最高 1,000,000 Mbps。使用 CLI 时运行 `limit set`（见 [CLI](cli.zh-CN.md#设置节点限速)）。

保存的值成为该节点的目标上限：立即生效，结束这项限速正在进行的自动降速，执行节点重启后仍然保留。部分节点未确认时，对话框保持打开，显示未确认的节点数，并逐行列出这些节点及原因：超时等常见原因会翻译，其他原因按节点报告的原文显示。

**每行显示的内容。** **运行上限** 是节点当前实际执行的上限，只在自动降速期间低于目标。目标值等于配置值（`nodeControl` 中的值或内置默认值）时标为 **配置目标**，在控制台或 CLI 中保存为其他值后标为 **已保存目标**。**实测速率** 是最近 5 秒内平均每秒发出的请求数（含重试）；带宽行是每秒从源端读取的数据量。限速名称旁的标签显示其[状态](#限速状态)。

**配置文件。** 上述默认值内置在执行节点中。要修改，在执行节点的 `service.json`（Linux 上为 `/opt/oss-transfer/agent/config/service.json`，见[路径](install.zh-CN.md#路径和端口)）中添加 `nodeControl` 对象，填写 `listQps`、`putQps`、`headQps`、`bandwidthBitsPerSecond`（单位 bit/s）中需要修改的键。0 表示不限速，省略的键保持默认值。新安装的执行节点没有 `nodeControl` 对象；从 V4 转换的执行节点已有包含全部四项上限的 `nodeControl`。修改后重启执行节点生效：

- 在控制台或 CLI 中保存过的上限保持保存的值，而且无法重置：再次保存配置中的值会重新显示 **配置目标**，但该值仍按已保存处理。例外是从未保存过、且正按配置值运行的上限：此时保存同一个值不会被记录，之后修改 `service.json` 仍会对它生效。
- 开启（从 0 改为正数）、调低或关闭（改为 0）请求上限后立即生效；如果该上限正在自动降速，且新目标不高于当前运行上限，这次降速随之结束。
- 调高的请求上限逐步生效：重启后该行先显示 *自动降速*，再显示 *逐步恢复*，运行上限每 10 秒提高 20%，直到达到新值。
- 修改 `bandwidthBitsPerSecond` 后立即生效（带宽从不自动降速）。带宽按整字节每秒执行，不是 8 的倍数的值向下取整（例如 500000004 变为 500000000 bit/s）。

在控制台或 CLI 中修改无需重启。用 Docker 安装的执行节点没有 `service.json`，按默认值启动。同一文件中的 `comparison` 对象用于限制执行节点保留的比对结果（见[结果的保存和清理](#结果的保存和清理)）。

**请求上限是平均速率。** 节点和任务的请求上限都按均匀间隔放行请求，每 1/速率 秒一个，没有突发额度，因此可以使用小数：0.5 表示每 2 秒一个请求。节点限速最低 0.01 次/秒，任务限速最低 0.000001 次/秒。任务限速在其执行节点之间分配，每个节点按自己的份额计算间隔：两个忙节点共用 0.5 次/秒时，各自每 4 秒发出一个请求。在任务限速下，节点上每类请求的第一个也要先等待一个间隔。实测速率按 5 秒平均，每个节点以 0.2 次/秒为单位变化：每秒发出 0.5 个请求的节点显示为 0.4 或 0.6。

### 任务限速在节点间的分配

任务限速在 **创建迁移** 页面的 **迁移选项 → 任务限速** 中设置，之后可以在任务详情中点击 **调整**（任务未设置带宽上限时显示为 **限速**）修改，或使用 `task limits`（见 [CLI](cli.zh-CN.md#创建任务和设置限速)）。**任务带宽上限** 为 0.1–1,000,000 Mbps，留空时只受节点限速约束。**LIST / GET QPS** 限制列举和所有对象 GET（含区间读取）；**HEAD QPS** 限制元数据请求；**PUT QPS** 限制上传，包括分片上传请求。QPS 留空或为 0 表示不限制该类请求。已停止或已结束的任务不能修改限速；已停止的任务恢复时沿用原来的限速。

任务详情以 **请求上限（任务总计）** 显示限速，最多保留六位小数。**请求速率** 表格按请求类型显示：

- **实时**：最近 5 秒内平均每秒的请求数（含重试）。GET 只统计对象读取，LIST 包括列举分片。
- **任务上限**：任务设置的上限。
- **生效上限**：各节点最多能发出的请求数。HEAD 和 PUT 为各节点“任务份额”与“节点上限”中较低者之和；LIST / GET 只累加任务份额，因为节点 LIST 上限不覆盖 GET。节点上限还由其他任务共用，实际上限可能更低。

表格保留一位小数，低于 0.05 次/秒的上限显示为 0。只有所有节点都上报时才显示速率。

任务的带宽限速以及集群范围的 LIST / GET、HEAD、PUT 限制都是整个任务的总量。Master 在任务运行期间按需求把总量实时分给活动节点。满足以下任一条件的节点算作忙：

- 还有未完成的子任务；
- 还能接收新工作：扫描仍在进行，或者还有批次等待分配；
- 正在参与排队移交；
- 是尚未完成的扫描的扫描节点。

任务不在运行状态时（例如正在恢复或停止），以及已隔离节点的工作或扫描正在转移时，所有节点都算作忙。其余节点算作空闲，只保留平分值的 1/64（至少每秒 1 字节）；剩下的总量由忙节点平分，同时不超过任何按节点设置的上限。例如两个节点共用 1000 Mbps：一个节点做完了工作，另一个还在传最后一个大对象时，空闲节点会释放份额，忙节点得到约 992 Mbps，而不是 500 Mbps。节点要在连续两次调度（约半秒）中都空闲才算空闲。重新收到工作的节点，在其他节点确认降额后立即提额。

任何时刻，各执行节点可能执行的份额之和都不会超过任务上限。先降低节点的份额；该节点确认新值之后，它让出的部分才会分给其他节点。调低限速期间，总和不超过原来的上限，并随着各节点确认逐步降到新上限。离线节点保留它最后的份额，直到它确认；启用租约隔离的任务在其执行租约到期、节点被隔离后释放，没有租约隔离的任务要等它重新连接。按节点限制（`PER_NODE` 范围）不参与分配，节点自身的带宽和请求限制仍然生效。

带宽限制（任务在节点上的份额，以及节点自身的带宽限制）按一段时间执行，而不是在每个瞬间执行。传输暂停后（例如等待较慢的磁盘写完），可以暂时读得比限额快，补回暂停的部分，但最多补回 100 ms 的限额（至少 64 KiB，至多 16 MiB）。因此在任意一段时间内，执行节点读取的字节数大约不超过限额乘以这段时长再加上这一额度；新设置或刚修改的限额不带这部分额度。这样即使目标端偶尔短暂停顿，限速任务也能用满几乎全部份额。请求限制没有这种额度，请求按均匀间隔发出。

执行节点对话框和 `task nodes` 显示每个节点的当前份额和需求：*按需（忙）* 或 *空闲（已释放）*。*调整中：等待节点确认降额* 表示该节点在确认降额之前仍持有原来较大的份额。按平分计算限速的旧版 Master 不显示需求。忙节点可以分到几乎全部限速，但单个大对象未必用得满：下载到本地目录时，按约一秒的节点份额并行拉取区间；设置了任务级带宽、LIST / GET 或 PUT 限制的任务写入对象存储时，每个对象按一个流传输，受单个连接的吞吐限制（见[大对象](#大对象)）。

Master 从按平分分配限速的版本升级时，已经在运行的任务会继续平分，直到所有节点都确认了平分值，之后切换为按需分配。执行节点无需升级，执行节点协议没有变化。

**降级 Master。** 旧版 Master 按平分计算限速，并使用更新的限速修订号，执行节点会接受。此时各节点份额之和可能短暂超过上限（最多为每个节点的动态份额加平分份额）。如需避免这段时间，降级前先停止运行中的任务。

### 存储限流

客户端请求过多时，存储服务会限流：返回 HTTP 503 或 429，或者返回 `SlowDown`、`Throttling`、`RequestLimitExceeded`、`TooManyRequests` 等错误码（无论状态码是什么）。这时执行节点会等待一段时间后重试该请求，并降低自己这类请求的上限，限流停止后再逐步回升。

因此，短暂的限流不会导致对象失败。在存储服务的日志中看到 503 或 429，或在限速历史中看到降速，只说明执行节点放慢了速度，并不代表对象失败。

#### 重试

被限流的请求最多尝试 10 次。每次重试前随机等待，上限依次为 1、2、4、8、16 秒，之后为 20 秒：10 次尝试平均共等待约一分钟，最多 111 秒。每次重试都要重新通过节点和任务的请求上限，因此重试也会随上限放慢。临时故障（例如连接被拒绝、重置或中止、超时、DNS 临时故障，或 501 和 505 以外的 HTTP 5xx；以及已应答过的主机上连接在收到响应前结束或主机名不再能解析）同样最多尝试 10 次，但每次至少等待上限的一半，因此总计约 1 到 2 分钟，足以等存储服务重启完成（见[存储服务中断](#存储服务中断或网络断开)）。其他可重试错误仍为 3 次。限流和临时故障的重试都不消耗 S3 SDK 的重试配额；停止任务会立即结束正在等待的重试。

对象请求（GET、HEAD 或 PUT）第 10 次尝试仍被限流时，该对象记为失败，错误信息包含 `exceeded maximum number of attempts, 10` 和错误码（例如 `SlowDown`）。限流缓解后重试这些对象即可（见[运行中任务重试失败项](#运行中任务重试失败项)）。大对象的区间只在响应体中断时重新读取，每个区间最多读取三次（含首次），因此一个区间最多发出 30 个 GET 请求。

列举请求第 10 次尝试仍被限流时，扫描会带着该错误停止；按文件清单或单个对象迁移的任务在扫描时查询对象的 HEAD 请求也是如此。已列举的对象处理完后，任务结束为部分失败（没有任何对象迁移成功或被跳过时为失败）。尚未列举的对象不会记为失败对象，因此任务运行期间重试失败项不会迁移它们。请在任务结束后重试任务，扫描会从停止的位置继续（见[断点续扫](#断点续扫)）。

#### 自动降速

每个执行节点按 LIST、PUT、HEAD 上限分别统计最近 5 秒内的限流响应。某项上限的限流响应至少 5 次、且不低于该类响应的 1% 时，执行节点降低这项上限。期间的成功响应不会让计数清零，因此大量并发请求中夹杂的限流也能识别；零星的限流（例如 1,000 个响应中有 5 个）则不会触发降速。

新上限是“运行上限”与“最近 5 秒中单秒最多发出的该类请求数”二者较小值的 90%，因此远高于实际流量的上限会立即降下来：上限 1,000 次/秒、流量峰值 300 次/秒时，降为 270。降速不会低于 200 次/秒（目标更低时不低于目标）；已处于该下限的上限和不限速的上限不会降低，默认 100 次/秒的 LIST 上限即属此类。降速后，同一上限 5 秒内不会再次降低，而且需要新的限流响应，因此一次突发只降一次。

自动降速只改变运行上限；目标上限、任务限速和带宽上限都不会被自动调整。被限流的对象 GET、列举分片和中止分片上传会重试，但不降低任何上限；对象 GET 可用任务的 LIST / GET 限速加以限制。每个执行节点独立识别限流、调整自己的上限；执行节点重启后，正在进行的降速继续保留，除非 `service.json` 中该上限的新目标不高于当前运行上限或为 0。

如果限流反复出现，请在使用该存储桶的所有执行节点上把上限设到开始限流的速率以下，或者限制任务的速率。调节详情中的 **降速前实测速率** 显示了这一速率。

#### 恢复

限流停止后，降低的上限会逐步回到目标。第一步在最后一次达到上述降速条件的限流之后 10 秒进行；限流持续时会不断推迟。每步的幅度取决于距上次降速的时间：

| 距上次降速 | 每步提高 | 下一步 |
| --- | --- | --- |
| 不到 10 分钟 | 被限流时速率的 5% | 30 秒后；这 10 分钟内每再降速一次，间隔加倍，最长 8 分钟 |
| 10 分钟及以上，或执行节点重启后 | 运行上限的 20% | 10 秒后 |

降速后的上限是被限流时速率的 90%，所以前两步先回到该速率，之后再试探更高的速率。按默认设置，PUT 上限在 1,400 次/秒满速时被限流，会降到 1,260，10 秒后升到 1,330，再过 30 秒回到 1,400。缓慢试探使共用同一个存储桶请求上限的多个执行节点不会每隔几秒就再次被限流。在控制台或 CLI 中保存上限会立即结束降速。

#### 限速状态

**执行节点** 页面上的每个限速行，以及 `limit list` 的每一行，都会显示状态：

| 控制台 | CLI | 含义 |
| --- | --- | --- |
| *自动降速* | *已降速* | 因限流而降低，持续到第一次回升，至少 10 秒 |
| *逐步恢复* | *恢复中* | 已至少回升一次，仍低于目标；再次降速时回到 *自动降速* |
| *已恢复目标* | *已恢复* | 最近一分钟内回到目标 |
| *按目标运行* | *正常* | 按目标上限运行 |
| *不限速* | *不限速* | 未设上限（目标为 0） |
| *状态待确认* | — | 自动刷新已暂停、最近一次读取失败，或节点状态已超过 30 秒（刷新间隔的两倍更长时，以两倍为准）未更新；显示的是上次读取的值 |

带宽不会自动调整，因此带宽行只显示 *按目标运行* 或 *不限速*（或 *状态待确认*）。请求上限处于降速或恢复中时，该行显示进度条（**运行上限 / 目标上限**），节点卡片显示 *节点可能遭遇限速，已自动调整运行上限。* 和 **查看详情**。控制台的其他页面会为每个这样的节点显示一条横幅；节点上限降低、回升或回到目标时，任何页面都会弹出通知。

#### 限速历史

**执行节点** 页面的 **限速历史** 页签按时间倒序列出所有节点最近的 50 条调整，包括运行上限的变化、阶段（*手动设置*、*自动降速*、*逐步恢复* 或 *已恢复目标*）、依据和当时的目标。降速的依据给出窗口内的限流响应数及其占比，例如 *OSS 限流响应（HTTP 503、429 或 SlowDown 等）：5 秒内 12 次，占该类请求的 2.4%。*

点击 **查看详情** 打开 **调节详情**：触发本次降速的请求（操作、任务、存储桶、对象 Key、HTTP 状态码、错误码，以及可提供给存储服务商的请求 ID）、触发条件，以及本轮调节的每一步。**每次恢复幅度** 显示距上次降速 10 分钟后使用的幅度（默认 20%）；在此之前，每步是上文所述较小的试探。较早版本留下的记录只显示 HTTP 503 的计数。

每个执行节点在数据库中保存全部调整记录。使用 CLI 时，`limit history --limit 200` 最多列出 200 条，`limit adjustment` 显示某一轮调节（见 [CLI](cli.zh-CN.md#设置节点限速)）。

#### 调整自动降速参数

执行节点的 `service.json` 中，`nodeControl` 下的 `autoAdjust` 对象用于调整上述规则，省略的键保持默认值：

| 键 | 默认值 | 作用 |
| --- | --- | --- |
| `throttleThreshold` | 5 | 窗口内触发降速所需的限流响应数（1–1,000,000）；旧名称 `consecutive503Threshold` 仍然有效 |
| `throttleRatio` | 0.01 | 限流响应至少要占该类响应的比例（大于 0，不超过 1） |
| `throttleWindowMs` | 5000 | 统计窗口的长度，也是同一上限两次降速之间的最短间隔（1,000–60,000，向上取整到整秒） |
| `reduceFactor` | 0.9 | 降速系数（大于 0 且小于 1） |
| `minQps` | 200 | 降速能达到的最低值；目标不高于它的上限不会被降低（大于 0） |
| `recoveryIntervalMs` | 10000 | 第一次回升前的等待时间，以及距上次降速 10 分钟后每步的间隔；试探间隔为它的三倍 |
| `increaseFactor` | 1.2 | 距上次降速 10 分钟后每步的系数（大于 1） |

例如，要让默认的 LIST 上限也能自动降低，把 `minQps` 设到 100 以下。把该键加到现有的 JSON 对象中，并保留其他键：

```json
"nodeControl": {
  "autoAdjust": { "minQps": 20 }
}
```

`minQps` 不低于所有目标时，任何上限都不会被降低，但被限流的请求仍会重试。存在未知的键或无效的值，或者 `throttleThreshold` 与 `consecutive503Threshold` 不一致时，执行节点无法启动。请先检查文件，再重启执行节点：

```sh
sudo /opt/oss-transfer/agent/bin/oss-transfer-agent --config /opt/oss-transfer/agent/config/service.json --check-config
sudo systemctl restart oss-transfer-agent
```

### 大对象

在单个执行节点内，128 MiB 及以上的对象不走单一数据流，而是拆成多个字节区间并行传输。写入对象存储时，各区间作为分片上传；下载到本地目录时，以 8 MiB 为一段并发拉取，但临时文件严格按顺序写入，与单一数据流相同：先到的区间在内存中等待，直到前面的区间写完。因此网络文件系统和 FUSE 文件系统看到的写入方式与单流下载一致，不会因为分散写入而变慢。所有区间都写完后，文件才以最终文件名出现（见[临时文件](#临时文件)）。

每个对象保证 4 路并发区间，节点有空闲对象并发时可以借用更多，合计最多 16 路。因此单个大对象可以用满原本空闲的节点，而繁忙节点也不会超额并发。每个进行中的区间都占用执行节点的 256 MiB 传输内存预算，该执行节点上的所有上传和下载共享这一预算。下载的区间在写入之前一直占用其并发槽和内存，所以每个对象最多在内存中保留 16 段（128 MiB）；磁盘写入跟不上时，拉取会暂停。

从对象存储读取时，每个区间都是一次固定在源对象版本上的独立条件 GET 请求。它计入任务的 LIST / GET 请求限制（节点请求限制不覆盖对象 GET，节点带宽限制仍然生效）；传输期间源对象发生变化时，该对象失败。中断的区间会重新拉取，每个区间最多读取三次（含首次）。不支持条件字节区间读取的存储按单一数据流读取。实时进度合计所有区间已传输的字节；某个区间重新拉取时，进度不会回退。

限速同样约束下载到本地目录时的区间。每个对象占用的区间最多相当于它在本节点约一秒内可读取的量：任务在本节点的带宽份额与节点带宽限制中较低的一个，除以 8 MiB 区间大小；设置了 LIST / GET 限制时，区间数也不超过任务在本节点每秒可发的 GET 数；最多 16 段。每秒不足两段（16 MiB/s，约 134 Mbps，或每秒 2 个 GET）时，该对象按单一数据流下载。这一点在对象开始时决定；之后每拉取一个新区间前都会重新检查窗口，份额或节点限速降低时窗口立即缩小。区间在等待限速时占用内存，因此窗口使每个对象占用的共享内存不超过它约一秒能读取的量，同一对象的所有区间合计也不会超过份额。任务设置了任务级带宽、LIST / GET 或 PUT 限制时（只设置 HEAD 限制不算），写入对象存储的每个对象按单一数据流传输；只有节点限速时不会改为单流。

设置了带宽限制时，下载到本地目录的同一对象的各区间按偏移从小到大优先使用带宽，因此它们按写入顺序陆续完成，而不是在窗口末尾一起完成。某个区间等待满 10 秒后会优先读取，以免服务端或代理因长时间读不到数据而关闭它已打开的请求。

#### 分段下载选项

下载任务（对象存储到本地目录）在 **创建迁移** 页面的 **迁移选项** 中有 **分段下载** 选项：**自动（默认）** 或 **停用**。自动即上文所述的方式，适合几乎所有任务。只有当并行区间读取造成问题时才选择停用，例如存储会限制大量并发 GET 请求、执行节点内存不足，或技术支持建议时；此后该任务的每个对象都按单一顺序数据流下载。该选项在创建任务时确定，停止、恢复、重试和更换节点后保持不变。下载到本地目录的任务会在任务详情和 `task show` 中显示该选项；该选项出现之前创建的任务按自动处理。

使用 CLI 时，在 `task create oss-to-local` 中加上 `--ranged-download off`（见 [CLI](cli.zh-CN.md#创建任务和设置限速)）。在 API 和导入文件中，任务请求行可写 `"rangedDownload": "auto"` 或 `"off"`；省略即为 auto，目标不是本地目录的任务不接受 `off`。任务详情和通过 **导出 JSON** 保存的任务行包含 `rangedDownload`。

该选项出现之前的执行节点从不分段下载，本身就等同于停用。滚动升级期间，Master 只把该选项发给报告支持它的执行节点；对不支持的执行节点，下次下发时会重新询问。未携带该选项下发的子任务按单一数据流下载每个对象，自动任务也一样，直到停止并恢复任务。这包括执行节点升级前接收的子任务，以及该选项出现之前的 Master 下发的子任务（即使接收的执行节点已经升级）。因此升级过程中不会丢失“停用”选择。

### 临时文件

下载到本地目录时，无论是否分段，数据都先写入临时文件；全部字节到齐并同步落盘后，才以最终文件名发布，因此失败、停止或中断的下载不会在目标位置留下不完整的文件。每个执行节点在它写入的每个目标目录中使用自己的隐藏暂存目录 `.oss-transfer-staging-…` 存放这些文件，并在写入前把该目录和每个文件登记到自己的数据库中。执行节点重启时会清理进程崩溃留下的临时文件；写入对象存储的分片上传同样会登记，因崩溃而未完成的分片上传会在重启时中止；因目标端不可用等原因中止失败的上传，之后会再次中止（见[存储服务中断](#存储服务中断或网络断开)）。没有任何执行过程再使用某个暂存目录时，执行节点会在子任务执行结束后删除它，并在启动时清理空的残留目录。扫描本地源目录时会跳过暂存目录。如果目标目录或其中的暂存目录被删除（例如任务期间删除并重新创建了目标目录），执行节点下次向该目录写入时会新建暂存目录。

### 失联节点

多节点任务中的执行节点失联后，未完成的子任务可以交给另一个已选定的节点。所有参与的执行节点都需要支持任务租约。Master 每 20 秒续期一次执行授权；失联的执行节点在 60 秒租约到期后停止启动新工作，并取消正在进行的传输。重新分配再等待 10 秒。执行节点对话框在该节点无法连接期间将其标记为 **离线**，其工作被接管后标记为 **已失联**。节点回来后，双方都支持恢复隔离机制且原共享目录仍可访问时，节点可以重新加入；在获得新一轮所有权之前，它的旧执行授权会先被撤销。旧版执行节点仍不会重新加入该任务。

恢复的节点既能接收新分配，也会分担健康节点上排队的子任务，扫描已经结束时也适用。重新分配沿用任务的分发策略，按剩余字节数加每个对象 64 KiB 估算负载。只有从未开始的子任务可以移交：Master 改变所有权前，当前节点必须原子地撤销其执行授权。正在运行和中断过的传输继续由当前节点处理。再均衡在恢复后分批进行，不会持续来回搬动队列。

接管支持对象存储之间的迁移和已验证的共享目录。每个共享目录保留一个很小的隐藏校验文件，以便其他节点确认看到的仍是原来的卷。独占的本地目录、校验文件丢失或旧版执行节点都会阻止自动重新分配。已完成的子任务保持不变；未完成的子任务保留编号和已保存的文件结果，新节点检查已完成的对象后继续。扫描节点故障时，由其他节点接管扫描（见[扫描接管](#扫描接管)）。

对象存储已经接收的请求可能在客户端取消后才完成，因此无法保证在任意 S3 服务上恰好写入一次。迁移期间源数据应保持稳定。启用任务租约后数据库格式升级为 schema 5；安全地重新加入已退出的节点需要 schema 8，凭证加密需要 schema 9，排队移交需要 schema 10。降级需要同时恢复 Master 和执行节点升级前配套的数据库备份。

### 调整任务的执行节点

打开任务，进入 **执行信息 → 执行节点 → 编辑节点**，或使用 [`oss-transfer-cli task nodes`](cli.zh-CN.md#调整任务的执行节点)。对应的 Master 接口为 `GET`/`POST /api/master/tasks/{id}/nodes`。对话框列出当前节点的状态、扫描节点、未完成的子任务，以及每个节点分得的任务带宽和 QPS 份额及其需求（见[任务限速在节点间的分配](#任务限速在节点间的分配)）。

**添加节点。** 只能添加在线、已注册且支持任务租约、恢复隔离和排队移交的执行节点，与自动接管使用同样的检查。旧版执行节点会列出但不可选，并说明原因；任务的现有节点版本过旧时，同样会拒绝；正在更新的执行节点要等更新完成后才能添加。上传和下载任务需要为每个新增节点填写任务共享目录的本地路径。系统执行与创建任务相同的预检：通过一个节点写入测试文件，再由现有节点和新增节点读取。新节点先处于 *加入中* 状态：Master 撤销它上面可能残留的旧授权、验证任务的共享目录校验文件并发放新的所有权轮次之前，它不会收到任何工作。之后它会接收后续子任务，从未开始的排队子任务也会按上文的排队移交机制转给它。向单节点任务添加节点时，系统先为该任务启用租约隔离；启用期间，现有节点正在进行的传输会短暂暂停，随后从已保存的进度继续。添加节点会把亲和分发的任务切换为均衡分发，使新增节点能分到工作，而不是只占用一份限速份额。

**移出节点。** 至少保留一个能接收工作的节点；加入中的节点不计入，因为它可能始终无法完成握手。替换节点时，请先添加新节点，等它加入后再移出旧节点。

- **平滑移出（推荐）**，即默认方式：该节点不再接收新子任务；它上面从未开始的排队子任务转给其余节点，所有权变更前由当前节点原子撤销；正在运行的子任务在它上面完成。之后节点离开任务。
- **立即移出**：立即撤销该节点的执行租约，取消其正在进行的传输。Master 收集这些子任务最后保存的进度，再通过接管流程由其余节点继续；已完成的对象只做校验，不重复复制。此方式需要支持接管（对象存储之间的迁移，或已验证的共享目录），否则会被拒绝。

如果某个节点失联时，其余唯一的节点正在排空，失联节点的工作会转给这个排空中的节点，由它执行或在离开前再次移交。离开的节点在任何工作移动前先被隔离：在线节点确认租约已持久撤销，并停止该任务的全部 I/O；离线节点按失联节点处理，租约到期后离开。没有租约隔离时（独占的本地目录，或执行节点不支持租约），它的工作无法转移，要等它重新连接并完成或移交工作后才离开。仍分配给它的失败子任务随之转移，由其余节点重试。如果它负责扫描，扫描转给其余节点（见[扫描接管](#扫描接管)）。已移出的节点不会自动重新加入任务；需要时请重新添加。

**进度。** 对话框打开期间按控制台的刷新间隔自动刷新，页面隐藏时暂停。刷新只更新节点状态、未完成的子任务和份额：已标记的节点、填写的本地路径和已通过的预检都会保留；确认步骤保持正在确认的摘要不变。每个节点行显示其调整进展：加入中的节点显示“正在完成握手与检查，加入后开始分配任务”；离开中的节点显示仍 *待完成或移交* 的子任务数；离线的待移出节点显示“节点离线，执行租约到期后离开，其任务由其他节点继续”，没有租约隔离时显示“节点离线，重新连接并完成或移交其任务后离开”。节点列表上方的说明显示扫描进展（见[扫描接管](#扫描接管)）。

所请求调整的各个阶段属于进度，而不是任务错误：离开的节点被隔离后拒绝工作、离线的待移出节点等待租约到期、扫描转到其他节点，以及刚加入的节点在第一次准备之前。意外失联或出错的节点仍会在任务上报告，并注明节点名称。任务详情只在运行问题持续约四秒后才显示（刷新间隔不超过四秒时，还需连续两次刷新都出现），并在它消失同样久之后才移除，因此单次协调产生又清除的问题不会闪现。已结束任务的错误会立即显示。节点仍持有旧限制时，任务的限速对话框显示 *正在同步限速设置…*，但只持续到 Master 尝试下发新限制为止；下发失败后显示 *部分节点未生效*，对话框外的这一警告同样遵循约四秒的规则。已知的运行消息按控制台语言显示；其他详情显示在已翻译的标签之后。

**带宽和 QPS。** 节点加入时，其他节点先确认降低后的份额；所有节点保留的份额之和不超过任务上限后，新节点才获得第一个执行租约。如果某个离线节点仍保留着它最后的份额，新节点先使用剩余的空间，待那份份额释放后再提额；只有完全没有剩余空间时，离线节点才会拖延加入。节点离开时，要等它被隔离后才提高其他节点的份额。排空中的节点只要还有子任务在执行，就保留自己的份额；没有子任务后降到空闲份额。任务带宽限速必须保证每个节点（包括加入中的节点）至少分得每秒 1 字节。

**限制。** 单对象任务、单文件上传、已完成的任务、已删除的任务和从旧版本迁移的任务不能调整节点。已停止或失败的任务可以调整，恢复运行时生效。任务尚未启用租约隔离时（例如运行中或已停止的单节点任务），调整要求所有现有节点在线，因为无法连接的节点上可能仍有未隔离的工作。任务正在停止或恢复时，请等状态稳定后重试。同一时间只能有一个调整在进行。有节点正在加入或排空时，Master 只接受以下调整，确保进行中的调整总能撤回：移出加入中的节点（取消加入）、在节点离开前重新添加排空中或立即移出中的节点（取消移出；本地传输沿用原路径，无需重新填写路径或预检）、立即移出排空中的节点、移出工作已被接管的失联节点。其他调整在上一次调整完成前都会被拒绝。每次调整都带有请求标识和所依据的成员版本，因此重试的请求只生效一次，依据过期信息的调整会被拒绝。调整保存在 Master 数据库中，Master 或执行节点重启后继续执行。第一次调整会把 Master 数据库格式升级到 schema 11。

### 运行中任务重试失败项

运行中的任务可以不停止而重试失败的对象。在任务详情或 **异常记录** 页面选择 **重试失败项**，或在 CLI 中运行 `task retry <ID>`。Master 会在任务当前这次运行中，把每个含失败对象的已结束子任务（FAILED 或 PARTIAL_FAILED）在原节点上重新打开：只重新传输失败的对象，已成功和已跳过的对象保留结果，任务的其余部分继续传输。重新打开的子任务按节点的并发上限排队执行，并使该节点在任务带宽和 QPS 分配中计为繁忙。异常记录先显示 **重试中**，随后显示结果。

仍在运行的子任务在结束前保留其失败对象，结束后可再次重试。正在移出任务的节点上的子任务会被跳过，由接管其工作的节点重试。重复请求不会重复打开同一个子任务。重试期间请求停止时，重新打开的子任务随任务一起停止，其对象显示 **重试未完成**。这些节点需要升级到本版本；对旧版执行节点，Master 会说明原因，并保持其子任务不变。每次请求最多重新打开 64 个子任务，更多时请再次重试。已停止、失败和部分失败的任务仍使用原有的重试，即恢复任务（见[重试、继续与恢复](#重试继续与恢复)）。

### 断点续扫

停止任务或重启负责扫描的执行节点后，扫描位置保存在执行节点数据库中。对象存储的扫描从保存的分页游标继续。本地扫描重新打开当前目录路径，跳过已完成的子目录和已处理的文件。当前目录特别大时，重启后仍需读取并排序其中的文件名；断点之前的文件不会逐个检查。文件清单任务同样保存处理位置。

断点与之前的扫描结果一起提交。重启后可能回放一小段尚未提交的内容，生成子任务前会先去重。断点只为每个任务增加有限的遍历状态，不会额外保存一份完整的文件名清单。升级负责扫描的执行节点后启用此功能。旧版本中尚未完成、也没有断点的扫描，需要一次兼容重扫来建立第一个断点。

续扫延续同一轮遍历，已遍历过（位于断点之前）的位置上发生的变化可能不会被发现。需要固定数据集时，应保持源端不变或使用快照。对象存储拒绝游标或当前本地目录被替换时，扫描会报错停止，而不是静默地从头开始或跳过数据。已完成的扫描在恢复传输时不会重复。

#### 扫描接管

扫描节点离开任务或失联时，待原扫描节点被隔离后，由其余节点接管扫描。Master 保留已保存分配所覆盖的断点。新的扫描节点根据这些分配重建扫描索引，从它们覆盖的最后一个源端分页断点继续，这个位置可能落后于原执行节点私有的扫描位置；从未交给 Master 的预扫描结果会重新列举，但不会下载对象内容。没有可迁移断点的任务仍需兼容重扫。共享本地目录在各节点上的路径可以不同，但原卷和当前目录的身份必须一致。扫描已经结束且所有批次都已分配时，不再需要扫描节点，也没有需要转移的内容。

执行节点对话框只把正在扫描或正在接管扫描的节点标记为 **扫描节点**，并用一条说明显示扫描进展：新扫描节点重建期间显示“正在移交扫描，从 Master 保存的断点继续”；原扫描节点已被隔离、新扫描节点尚未开始时显示“原扫描节点已退出，其他节点将从 Master 保存的断点接管扫描”；所有批次都已分配后显示“扫描已完成，不再需要扫描节点”，并带有 *扫描已完成* 标签。`task nodes` 和 `task show` 会输出对应的说明。

### 数据库空间

Master 持久保存、确认并授权释放扫描批次后，执行节点才释放这些批次。扫描完成后，也会在后台释放去重索引。永久删除任务时，同时释放其扫描和执行记录。释放的页面会被重复使用；需要缩小已有数据库文件时，见[数据库维护](database-maintenance.zh-CN.md)。
