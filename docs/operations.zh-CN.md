# 并发、比对与更新

[English](operations.md)

## 节点并发

打开 **执行节点 → 编辑节点**，可调整子任务并发和每个子任务内的对象并发。默认分别为 32 个子任务、每个子任务 4 个对象，即单节点最多同时传输 128 个对象；已有的保存配置继续保留。

修改立即作用于运行中的任务，重启后保留。调低上限时，已发出的请求先完成，再按新上限调度。网络利用不足时调高可能有帮助；节点和任务的带宽、QPS 限制仍然生效。子任务并发范围为 1–64，对象并发为 1–32，两者乘积不能超过 256。

## 对象比对

在 **运维工具 → 对象比对** 中，两侧各选择单个对象或存储桶/前缀。前缀比对时，源前缀替换为目标前缀：源 `images/` 下的 `images/a.jpg` 对应目标 `backup/` 下的 `backup/a.jpg`。前缀为空表示整个存储桶。两侧缺失的对象都会记录。

**元数据** 模式通过 HEAD 请求比较大小和可迁移的元数据，不读取对象内容，不能据此确认字节一致。ETag 不作为跨厂商通用的内容哈希：分片上传和不同的存储服务可能对相同内容生成不同的 ETag。

**内容** 模式从两端流式读取对象并计算 SHA-256，不生成本地对象文件，但会在网络上完整传输两端内容，可能产生存储读取费用。读取过程中发生变化的对象单独标记。整个存储桶的比对不是原子快照；需要确认某一固定数据集时，请先暂停写入。

每个 Agent 同时执行一次比对。结果分批保存，只保留差异和错误。每个节点保留最近 10 次比对，每次保留前 10,000 条差异。超过上限后仍继续计数，页面会提示结果已截断；可缩小前缀查看其余差异，或删除已结束的比对结果。

## 更新已安装的服务

打开 **运维工具 → 版本更新** 更新 Master，然后在 **执行节点 → 版本更新** 点击 **更新全部节点**，把可升级的 Agent 更新到 Master 的版本。每个节点需以目标版本重新连接并完成更新，才会开始下一个；更新失败时队列停止。队列保存在 Master，关闭页面或重启 Master 不会丢失。也可以单独更新某个节点。

尽量等运行中的任务结束后再更新。需要带任务升级时，先更新 Master，再逐台更新 Agent。原生安装器在停止服务前，会请 Master 在升级期间保留该 Agent 的任务。验证启动成功或回滚成功后解除保留；安装器无法完成时，保留最多 30 分钟后过期。旧版 Master 需先升级，Agent 安装器才能使用这项保护。

在线替换适用于受管的原生安装。更新程序校验发布包，在停止服务前完成下载，再由独立进程运行原生安装器。安装器临时备份程序、配置、服务定义和已停止的数据库；新服务通过健康检查并确认安装后删除备份。启动失败时，尝试恢复之前的安装，并保留恢复文件。重启中断的 Agent 传输会在重新连接后继续。

备份写入本机的[默认备份目录](install.md#paths-and-ports)，即使历史安装保存过共享存储路径。显式传入 `--backup-dir`（PowerShell 为 `-BackupDir`）可选择其他目录。停止服务前，安装器清理符合条件的备份并检查可用空间。**升级备份 → 清理备份** 可删除已完成的升级备份；失败的备份和缺少完成标记的旧备份会保留。数据库备份每 10 秒打印一次进度，包括最后的磁盘同步。

计划降级时，升级前请另行备份每个服务的程序、配置和已停止的数据库；成功升级后不会留下回退副本。自动回滚未能完成时，参阅[手动恢复](#升级失败后恢复)。

尚不支持在线更新的版本，第一次升级仍需使用安装脚本。容器部署使用 [Docker Compose 更新](docker-compose.md)；在运行中的容器内替换二进制文件，会在容器重建时丢失。

## 升级失败后恢复

使用安装器打印的备份目录。停止受影响的服务，然后运行一个能同时读取当前和备份数据库格式的 Master 或 Agent 程序，参数为 `--config <备份目录>/service.json --restore-state <备份目录>/database`。如有 `database.key`，请与快照放在一起。该命令把数据库恢复到保存的配置所记录的数据目录。如果已安装的数据库丢失了密钥，请先从同一数据库的备份中恢复对应的 `master.db.key` 或 `agent.db.key`。

把保存的程序、配置、安装元数据、服务定义和 CLI 恢复到原位置，然后启动服务。已传输的文件保持原样。自行备份时，请停止服务，复制其配置和数据目录（包括 `master.db.key` 或 `agent.db.key`）；计划降级时，保留对应版本的程序。

## 重置管理员密码

默认 Linux 安装：

```sh
sudo systemctl stop oss-transfer-master
sudo /opt/oss-transfer/master/bin/oss-transfer-master \
  --config /opt/oss-transfer/master/config/service.json --reset-admin-password
sudo systemctl start oss-transfer-master
```

使用打印出的密码登录，然后设置新密码。在其他系统上，停止服务后用同样的参数运行 Master 程序。如果自定义过安装路径，请使用实际路径。

## 失联节点

多节点任务中的 Agent 失联后，未完成的子任务可以交给另一个选定节点。所有参与的 Agent 都必须支持任务租约。Master 每 20 秒续期一次执行授权；失联的 Agent 在 60 秒租约到期后停止启动新工作并取消正在进行的传输。Master 再等待 10 秒后重新分配。双方都支持恢复隔离、且原共享目录仍可访问时，返回的节点可以重新加入。程序先撤销它的旧执行授权，再发放新的所有权轮次。旧版 Agent 不会重新加入该任务。

恢复的节点可以接收新子任务，也会分担健康节点上排队的子任务，扫描已经结束时也适用。重新分配沿用任务的分发策略，按剩余字节数加每个对象 64 KiB 估算负载。只有从未开始的子任务可以移交：当前节点必须先原子撤销其执行授权，Master 才变更所有权。运行中和已中断的传输保留在当前节点。再均衡在恢复后分批进行，不会持续来回搬动队列。

接管支持 OSS→OSS 和已验证的共享目录。每个共享目录中保留一个很小的隐藏校验文件，以便其他节点确认仍能访问原来的卷。独占的本地目录、校验文件丢失或旧版 Agent 都会阻止自动接管。已完成的子任务保持不变；未完成的子任务保留编号和已保存的文件结果，新节点先校验已完成的对象再继续。扫描节点故障时，接替节点根据 Master 保存的分配重建扫描索引，并从这些分配覆盖的最后一个源端分页断点继续扫描。从未交给 Master 的预扫描结果需要重新发现；这项检查不下载数据内容。

对象存储已接受的请求可能在客户端取消后才完成，因此在任意 S3 服务上，接管无法保证写入恰好一次。传输期间应保持源数据稳定。启用任务租约会把数据库格式升级到 schema 5；安全地重新加入已退出的节点需要 schema 8，凭证加密需要 schema 9，排队移交需要 schema 10。降级需要同时恢复 Master 和所有 Agent 升级前的配套数据库备份。

## 调整任务的执行节点

打开任务，进入 **执行信息 → 执行节点 → 编辑节点**，或使用 [`oss-transfer-cli task nodes`](cli.zh-CN.md#调整任务的执行节点)。对应的 Master 接口为 `GET`/`POST /api/master/tasks/{id}/nodes`。对话框列出当前节点的状态、扫描节点、未完成的子任务，以及每个节点实际分得的任务带宽和 QPS 份额。

**添加节点。** 只能添加在线、已注册且支持任务租约、恢复隔离和排队移交的 Agent，与自动接管使用同样的检查。旧版 Agent 会列出但不可选，并说明原因；任务的现有节点版本过旧时，同样会拒绝。上传和下载任务需要为每个新增节点填写任务共享目录的本地路径。系统执行与创建任务相同的预检：通过一个节点写入测试文件，再由现有节点和新增节点读取。新节点先处于“加入中”：Master 撤销它上面可能残留的旧授权、验证任务的共享目录校验文件并发放新的所有权轮次之前，它不会收到任何工作。之后它会接收后续子任务，从未开始的排队子任务也会按上文的排队移交协议转给它。向单节点任务添加节点时，系统先为该任务启用租约隔离；启用期间，现有节点正在进行的传输会短暂暂停，随后从已保存的进度继续。亲和分发模式下，新工作仍优先分给主节点；新增节点只承接排队工作和离开节点的工作。

**移出节点。** 至少保留一个节点。

- *排空*（默认）：该节点不再接收新子任务；它上面从未开始的排队子任务转给其余节点，所有权变更前由当前节点原子撤销；正在运行的子任务在它上面完成。之后节点离开任务。
- *立即*：立即撤销该节点的执行租约，取消其正在进行的传输。Master 收集这些子任务最后保存的进度，再通过接管流程由其余节点继续；已完成的对象只做校验，不重复复制。此方式需要支持接管（OSS→OSS 或已验证的共享目录），否则会被拒绝。

离开的节点在任何工作移动前先被隔离：在线节点确认租约已持久撤销，并停止该任务的全部 I/O；离线节点按失联节点处理，租约到期后离开。仍分配给它的失败子任务随之转移，由其余节点重试。如果它负责扫描，扫描从已保存分配覆盖的最后一个断点转到其余节点继续。已移出的节点不会自动重新加入任务；需要时请重新添加。

**带宽和 QPS。** 任务限制在活动节点之间平分。节点加入时，所有现有节点必须先确认已降低的份额，新节点才会获得第一个执行租约。节点离开时，要等它被隔离后才提高其他节点的份额。任务总量在任何时刻都不会超出。排空中的节点在离开前保留自己的份额。每个加入的节点至少需要分得每秒 1 字节的任务带宽。

**限制。** 单对象任务、单文件上传、已完成的任务、已删除的任务和从旧版本迁移的任务不能调整节点。已停止或失败的任务可以调整，恢复运行时生效。任务正在停止或恢复时，请等状态稳定后重试。同一时间只能有一个调整在进行。有节点正在加入或排空时，Master 只接受三类调整：移出加入中的节点（取消加入）、立即移出排空中的节点、重新添加排空中的节点（取消排空）。其他调整在上一次调整完成前都会被拒绝。每次调整都带有请求标识和所依据的成员版本，因此重试的请求只生效一次，依据过期信息的调整会被拒绝。调整保存在 Master 数据库中，Master 或 Agent 重启后继续执行。第一次调整会把 Master 数据库格式升级到 schema 11。

## 数据库空间

Master 持久保存、确认并授权释放扫描批次后，Agent 会释放这些批次。扫描完成后，也会在后台释放去重索引。永久删除任务时，也会释放其扫描和执行记录。释放的页面会被重新使用；要缩小已有的数据库文件，请参阅[数据库维护](database-maintenance.md)。

## 续扫

停止任务或重启扫描节点后，扫描位置保存在 Agent 数据库中。OSS 扫描从保存的分页游标继续；本地扫描重新打开当前目录路径，跳过已完成的子目录和已处理的文件。单个当前目录特别大时，重启后仍需读取并排序其文件名，但不会逐个检查断点之前的文件。文件清单任务也会保存处理位置。

断点与之前的扫描结果一同提交。重启后可能回放一小段未提交的内容，生成子任务前会去重。断点只为每个任务增加有限的遍历状态，不会另存一份完整的文件名清单。升级负责扫描的 Agent 后即可启用此行为。旧版本中尚未完成且没有断点的扫描，需要一次兼容重扫来建立第一个断点。Master 也会保存已保存分配覆盖的断点；接替的扫描节点从这个位置继续，它可能落后于原 Agent 私有的扫描位置。没有可迁移断点的任务仍需兼容重扫。各节点的共享本地路径可以不同，但原卷和当前遍历目录的身份必须一致。

续扫延续同一轮遍历，断点之前的变化可能不会被发现。需要固定数据集时，请保持源数据不变或使用快照。OSS 拒绝旧游标、或当前本地目录被替换时，扫描会报错停止，不会静默地从头开始或跳过数据。已完成的扫描在传输恢复时不会重复。
