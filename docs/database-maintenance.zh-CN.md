# 数据库空间

[English](database-maintenance.md)

数据库文件随着迁移推进会越来越大。这一页说明数据库文件增长的原因以及如何回收磁盘空间。对象比对的结果不在数据库中，最后一节[比对结果](#比对结果)单独说明。如果还没有开始迁移，先查看[规划](planning.zh-CN.md)中的磁盘估算方法。

数据库保存的是对象名称、扫描断点、子任务分配和传输结果。对象内容在源端和目标端之间直接流式传输，不经过数据库，所以数据库的大小取决于对象数量，与单个对象的大小关系不大。小文件达到百万级时，这一点尤为明显。

扫描尚未结束时，数据库中保留一份索引，用于恢复时去重和检测源端变化。扫描完成后，执行节点（Agent）在后台以小事务分批删除这份索引。扫描批次另有一套释放规则：Master 把一个批次持久保存为子任务、确认接收并授权释放之后，执行节点在后台删除这个批次，即使扫描仍在进行也会删除。未确认的批次继续保留以便投递，重试和报告使用的执行记录也会保留。

永久删除一个任务，它的扫描和执行记录一并清除。但如果只是停止任务或移入回收站，这些记录仍然保留。

永久删除在后台执行，关闭页面或重启服务不会使该操作失效，之后仍会继续完成。清理完成之前，回收站页面会显示清理阶段、已删除记录数和已完成节点，CLI 使用 `oss-transfer-cli task trash` 也可以查看。离线的节点恢复后自动重试，已经移除的节点则保留自己的本地历史。清理只删除任务记录，不涉及源端和目标端的文件。

新写入的对象记录采用紧凑格式，较大的值在压缩能节省空间时才压缩存储。已有的未压缩记录仍然正常读取。删除和清理释放的数据页供后续写入复用，但数据库文件本身不会变小。要真正缩小文件，需要执行一次离线压缩，见[回收磁盘空间](#回收磁盘空间)。

Master 和执行节点的数据库中都存有存储凭证，用 AES-256-GCM 加密。每个数据库旁边有一个 `.key` 文件，只允许对应的服务账号和系统管理员读取。备份数据库时，密钥必须一并保存。如果只复制数据库，无法获取可用的凭证备份。这一机制保护的是数据库文件被复制、但密钥未被获取的情况。如果攻击者能同时读取两个文件，加密就起不到保护作用。

首次启动时，程序迁移已有的存储配置。旧的明文凭证可能还残留在数据库未使用的页中，执行一次离线压缩才能清除。压缩后的新数据库不再包含这些页，不过旧备份中的明文无法通过压缩清除，物理磁盘层面的擦除也无法保证。之后重启不会再重写整个数据库。

原生安装时，安装器在确认服务启动成功后才授权释放扫描副本。这样做是为了安全：万一升级回滚了 Master 的数据库，扫描副本仍然保留。旧版 Master 和安装器不具备授权释放的能力，它们已确认的批次一直保留。在授权前就已经结束的任务，也保留这些批次。

## 回收磁盘空间

压缩之前，先停止对应的服务，按[备份与恢复](operations.zh-CN.md#备份与恢复)做好备份。

压缩工具写入一个新文件，把数据页紧凑排列，转换旧版执行节点的扫描索引记录，压缩符合条件的值。写入完成后逐条校验所有记录，确认无误才发布新文件。原文件始终不变，已经存在的输出文件也绝不覆盖。压缩过程中每 10 秒输出一次进度。

以安装在默认 Linux 路径下的执行节点为例：

```sh
sudo systemctl stop oss-transfer-agent
sudo /opt/oss-transfer/agent/bin/oss-transfer-agent \
  --config /opt/oss-transfer/agent/config/service.json \
  --compact-state /opt/oss-transfer/agent/data/agent.compact.db
```

压缩成功后，保持服务停止，用压缩后的文件替换原文件。以下命令保留原文件的属主和权限，并且拒绝覆盖已存在的 `agent.before-compact.db`：

```sh
sudo cp --attributes-only --preserve=mode,ownership /opt/oss-transfer/agent/data/agent.db /opt/oss-transfer/agent/data/agent.compact.db &&
sudo mv -nT /opt/oss-transfer/agent/data/agent.db /opt/oss-transfer/agent/data/agent.before-compact.db &&
sudo test ! -e /opt/oss-transfer/agent/data/agent.db &&
sudo mv -nT /opt/oss-transfer/agent/data/agent.compact.db /opt/oss-transfer/agent/data/agent.db &&
sudo systemctl start oss-transfer-agent
```

启动后，先确认节点已重新连接、任务和报告仍然存在，再删除保留的原文件。压缩 Master 数据库的做法相同，将命令中的 `agent` 替换为 `master`。如果安装时自定义了路径和服务名，用实际值替换。

如果数据库是加密的，压缩还会写出 `agent.compact.db.key`，密钥和 `agent.db.key` 相同。替换文件时，保留原位置的 `agent.db.key` 即可。你保留的每一份数据库备份旁边都要存放一份密钥。确认服务启动正常后，可以删除多余的压缩副本密钥。

目标位置需要有足够空间容纳压缩副本。工具在每次写事务前检查剩余空间，至少预留 256 MiB 加上下一次数据库扩展需要的量。压缩一旦失败（空间不足是最常见的原因），工具会删除临时输出，原文件保持完好，使用原文件重启服务即可。维护期间其他程序也可能占用磁盘空间，应一并考虑。

每项功能对应一个 schema 版本：

| Schema | 功能 |
|--------|------|
| 4 | 紧凑存储 |
| 5 | 自动接管任务 |
| 6 | 释放已确认的扫描批次（执行节点数据库） |
| 7 | 接受后台删除 |
| 8 | 故障切换后执行节点重新加入任务 |
| 9 | 凭证加密 |
| 10 | 队列移交 |
| 11 | 调整任务的执行节点（Master 数据库） |

旧版程序无法打开它不支持的 schema 的数据库。如果需要降级，请同时恢复升级前制作的数据库备份和旧版程序。

## 比对结果

执行节点把对象比对的结果保存为文件，放在数据目录下的 `comparisons` 中（Linux 上是 `/opt/oss-transfer/agent/data/comparisons`），不写入 `agent.db`。数据库压缩不涉及这些文件。用 `--backup-state` 制作的数据库备份不包含它们，安装器的升级备份也一样。

执行节点自动清理这些结果：比对结束 30 天后删除，结果超过节点的存储预算时提前删除较早的。清理规则和配置方法见[结果的保存和清理](operations.zh-CN.md#结果的保存和清理)。

如果需要重新获取已删除的结果，重新比对即可，比对的是两端对象当时的状态。删除结果不影响任何任务、传输或已存储的对象。在控制台中点击 **删除比对结果**，或使用 CLI 的 `object delete`，均可删除。

如果要手动删除 `comparisons` 下的文件，先停止执行节点。直接删除文件后，对应的比对只剩各项计数，差异列表丢失，也无法再继续。页面显示*该节点上的比对结果已不可用*，导出标为不完整（`RESULTS_UNAVAILABLE`）。恢复较早的数据库后，执行节点启动时把每个比对的文件截回数据库记录的长度，并删除数据库中没有记录的比对文件。

4.1.40 及更早版本的执行节点在 `agent.db` 中为每次比对最多保存 10,000 条差异。升级后的执行节点仍能读取这些旧数据，并按同样的保留规则以小事务分批删除。和其他清理一样，释放的页面供后续写入复用，只有压缩才能缩小文件。
