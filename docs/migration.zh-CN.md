# 从 V4.0.x 升级到 V4.1.x

[English](migration.md)

V4.0.x 的数据需要先离线转换，才能在 V4.1.x 中使用。转换工具会保留账号、存储连接、节点限制、任务历史和回收站。未完成的任务进入新安装后处于已停止状态。

全新安装请参考[安装说明](../README.zh-CN.md)。已有的 V4.1.x 安装请使用[版本更新](operations.zh-CN.md#更新已安装的服务)。

## 转换现有安装

1. 停止旧 Master 和所有执行节点。备份每个节点的数据库和配置，包括环境变量和命令行参数中的覆盖配置。
2. 导出每个节点的 RocksDB 数据；如果旧 Master 也执行过传输，同样需要导出。
3. 编写迁移计划，写明节点身份、实际生效的限制、Master 地址和最终数据路径。
4. 在新目录中准备并完成转换。
5. 使用生成的 `service.json` 文件安装原生服务。确认 Agent 在线后，再恢复需要继续执行的任务。

具体命令和计划格式见[转换指南](development/legacy-migration.zh-CN.md)。准备和最终发布步骤可在 Linux 或 macOS 上运行，包括缺少 `renameat2` 的早期 CentOS / RHEL 7 内核。在新服务和任务结果检查无误之前，请保留原安装和备份。

V4.1.x 将调度与执行分离。单机部署时需同时安装 Master 和 Agent，两者使用各自的数据目录。集群部署时，把每个转换完成的 Agent 目录放到对应的执行主机上，路径与其配置中记录的绝对路径一致。

如果现有 Agent 的私有凭证与 Master 快照一致，它会保留原有身份。V4.0.x 中直接寻址的 worker 则通过迁移计划中的显式条目获得新身份。转换后使用原账号密码登录；旧的登录会话会失效。

## 恢复未完成的任务

首次恢复时，会按任务保存的范围、清单、过滤条件和目标命名规则，重新扫描任务原来的范围。在复用旧的成功结果之前，Agent 会读取当前的源端和目标端对象，比较 SHA-256 哈希，并检查读取期间两者的身份是否发生变化。

源端对象缺失时记为失败项。目标端已存在但内容不一致的对象，按保存的冲突策略处理：`SKIP` 保持不变；`OVERWRITE` 允许再次写入。历史上被时间过滤排除的对象继续排除。中断的分片上传对象会以对象为单位重新开始，因为旧数据库没有续传所需的上传 ID 和已完成分片列表。

已完成的任务保留历史结果和覆盖范围统计。新的传输尝试会单独记录结果。在计划中设置 `acceptGoRuntimeDefaults` 之前，请先查看转换指南中关于重试、并发和分片上传的默认值。
